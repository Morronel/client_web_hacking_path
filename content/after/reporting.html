Reporting & Responsible Disclosure

Writing Vulnerability Reports

A well-written vulnerability report is the difference between a security issue getting fixed quickly and one that languishes in a backlog. Whether you are submitting to a bug bounty program or coordinating with a vendor directly, the quality of your report determines its impact.

Essential Components of a Report

Every vulnerability report should include these key sections:

Section Description
Title A concise, descriptive title that identifies the vulnerability type and affected component (e.g., "Stored XSS in User Profile Bio Field")
Severity The assessed severity level using CVSS or the program's rating system
Description A clear explanation of what the vulnerability is, where it exists, and why it matters
Steps to Reproduce Numbered, precise steps that allow anyone to replicate the issue — this is the most important section
Impact What an attacker could achieve by exploiting this vulnerability (data theft, account takeover, etc.)
Remediation Suggested fixes or mitigations (input validation, parameterized queries, CSP headers, etc.)
Pro tip: Always include screenshots, HTTP request/response pairs, or video recordings when possible. Visual evidence makes your report significantly more convincing and easier to triage.

CVSS Scoring Basics

The Common Vulnerability Scoring System (CVSS) is the industry-standard framework for rating vulnerability severity. It produces a score from 0.0 to 10.0 based on several metrics:

Score Range Rating Example
0.0 None Informational finding
0.1 – 3.9 Low Information disclosure with limited impact
4.0 – 6.9 Medium Reflected XSS requiring user interaction
7.0 – 8.9 High SQL injection with data exfiltration
9.0 – 10.0 Critical Remote code execution, no authentication required

CVSS considers factors like Attack Vector (network, adjacent, local, physical), Attack Complexity (low, high), Privileges Required (none, low, high), User Interaction (none, required), and the impact on Confidentiality, Integrity, and Availability.

Important: Do not confuse CVSS with CVE or CWE. CVE (Common Vulnerabilities and Exposures) is an identifier system for known vulnerabilities. CWE (Common Weakness Enumeration) categorizes types of software weaknesses. CVSS is the scoring system for severity.

Responsible Disclosure

Responsible disclosure (also called coordinated disclosure) is the practice of privately reporting vulnerabilities to the affected vendor and giving them a reasonable timeframe to develop and release a fix before any public disclosure.

The 90-Day Standard

The widely accepted standard, popularized by Google's Project Zero, is a 90-day disclosure deadline. After reporting a vulnerability to a vendor:

  • The vendor has 90 days to develop, test, and release a patch
  • If the vendor patches within the deadline, disclosure happens after the patch is released
  • If the vendor fails to patch within 90 days, the researcher may publicly disclose the vulnerability
  • Extensions may be granted (typically 14 days) if a patch is imminent

Coordinated Disclosure Process

  1. Discovery: You find a vulnerability during authorized testing
  2. Report: You privately notify the vendor through their security contact or bug bounty program
  3. Acknowledgment: The vendor confirms receipt (ideally within 1–3 business days)
  4. Remediation: The vendor develops and tests a fix
  5. Disclosure: After the fix is deployed (or the deadline passes), details may be published

Bug Bounty Report Best Practices

Bug bounty programs have specific expectations. Following these practices will lead to faster triage, higher payouts, and a better reputation:

  • Read the scope carefully — only test assets that are in scope
  • One report per vulnerability — do not bundle multiple issues
  • Provide a proof of concept — demonstrate real impact, not theoretical risk
  • Avoid automated scanner dumps — triagers dismiss reports that are just scanner output
  • Be professional and patient — triage takes time; follow up politely after 1–2 weeks
  • Include environment details — browser version, OS, any special configuration needed

Good vs Bad Reports

Good report: "Stored XSS in the user bio field at /settings/profile. An attacker can inject <img src=x onerror=alert(document.cookie)> which executes when any user views the profile. This allows session hijacking of any visitor. Steps: 1. Log in as any user. 2. Navigate to /settings/profile. 3. Enter the payload in the bio field. 4. Save and view the profile."

Bad report: "Found XSS on your site. You should fix it. I can inject scripts. Let me know if you want more details."

Remember: Never exploit a vulnerability beyond what is necessary to demonstrate the issue. Do not access other users' data, do not exfiltrate real data, and do not cause disruption to services.
