Same-Origin Policy та CORS

Що таке Same-Origin Policy?

Same-Origin Policy (SOP) — найфундаментальніший механізм безпеки у веб-браузерах. Він обмежує спосіб, яким скрипти, завантажені з одного джерела (origin), можуть взаємодіяти з ресурсами іншого джерела. Без SOP будь-який сайт, який ти відвідуєш, міг би читати твою пошту, отримати доступ до банківського рахунку та вкрасти session cookies з кожного іншого сайту, де ти залогінений.

Визначення "Origin"

Origin визначається трьома компонентами: схема (протокол), хост (домен) та порт. Два URL мають однаковий origin тоді й тільки тоді, коли всі три компоненти точно збігаються.

URL A URL B Однаковий Origin? Причина
https://example.com/page1 https://example.com/page2 Так Однакові схема, хост і порт (443)
https://example.com http://example.com Ні Різна схема (https vs http)
https://example.com https://api.example.com Ні Різний хост (піддомен враховується)
https://example.com https://example.com:8443 Ні Різний порт (443 vs 8443)
http://example.com:80 http://example.com Так Порт 80 — типовий для http

Що SOP блокує, а що дозволяє

Cross-origin читання (ЗАБЛОКОВАНО за замовчуванням)

JavaScript на evil.com не може прочитати відповідь від fetch() або XMLHttpRequest до bank.com. Браузер надсилає запит, але блокує скрипту доступ до читання відповіді. Це запобігає крадіжці даних.

Cross-origin запис (ДОЗВОЛЕНО)

Форми можуть надсилати POST-запити на будь-який origin. Посилання переходять на будь-який origin. Саме тому можливі атаки CSRF (Cross-Site Request Forgery) — браузер охоче надсилає запит разом з cookies; він просто не дає зловмиснику прочитати відповідь.

Cross-origin вбудовування (ДОЗВОЛЕНО)

Ресурси на кшталт <img>, <script>, <link>, <iframe> та <video> можна завантажувати з будь-якого origin. Саме так працюють CDN — ти завантажуєш jQuery з cdn.jsdelivr.net, хоча твій сайт на іншому origin. Однак сторінка, що вбудовує ресурс, не може прочитати піксельні дані cross-origin зображення на canvas (tainted canvas).

SOP не запобігає запитам — він запобігає читанню відповідей. Сервер все одно отримує та обробляє cross-origin запит. Ця різниця є ключовою для розуміння CSRF та причин створення CORS.

CORS — Cross-Origin Resource Sharing

CORS — це механізм, який дозволяє серверам вибірково послаблювати Same-Origin Policy. Коли веб-додаток на frontend.com потребує викликати API на api.backend.com, сервер може включити CORS-заголовки, щоб повідомити браузеру: «дозволь цьому origin читати мою відповідь».

Прості запити

Для простих запитів (GET, HEAD, POST зі стандартними типами контенту) браузер надсилає запит напряму та перевіряє заголовки відповіді: 

Access-Control-Allow-Origin: https://frontend.com

Якщо заголовок відповідає origin запиту, браузер дозволяє скрипту прочитати відповідь.

Preflight-запити

Для «непростих» запитів (PUT, DELETE, кастомні заголовки, JSON content type) браузер спочатку надсилає OPTIONS-запит (preflight), щоб запитати дозвіл: 

OPTIONS /api/data HTTP/1.1
Host: api.backend.com
Origin: https://frontend.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: Content-Type, Authorization

Сервер відповідає дозволеними методами та заголовками:

Access-Control-Allow-Origin: https://frontend.com
Access-Control-Allow-Methods: GET, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 86400

Облікові дані та CORS

За замовчуванням cross-origin запити не включають cookies або HTTP-автентифікацію. Щоб їх включити, клієнт повинен встановити credentials: 'include' (fetch) або withCredentials = true (XHR), а сервер повинен відповісти: 

Access-Control-Allow-Credentials: true

Критичне правило: Коли Allow-Credentials: true, заголовок Access-Control-Allow-Origin НЕ МОЖЕ бути підстановочним знаком *. Він повинен вказувати точний origin. Браузери це перевіряють.

Помилки конфігурації CORS

Помилки конфігурації CORS — поширене джерело вразливостей. Ось найнебезпечніші патерни:

1. Відображення Origin

Сервер сліпо відображає заголовок Origin у Access-Control-Allow-Origin. Тепер будь-який сайт може читати автентифіковані відповіді: 

// Request from evil.com
Origin: https://evil.com

// Server response (vulnerable)
Access-Control-Allow-Origin: https://evil.com
Access-Control-Allow-Credentials: true

2. Дозволений Null Origin

Деякі сервери дозволяють origin null, вважаючи це безпечним. Але ізольовані iframe та локальні файлові сторінки надсилають Origin: null, що робить експлуатацію тривіальною: 

Access-Control-Allow-Origin: null
Access-Control-Allow-Credentials: true

3. Wildcard з обліковими даними (блокується браузерами)

Хоча Access-Control-Allow-Origin: * з Access-Control-Allow-Credentials: true відхиляється браузерами, деякі розробники обходять це, відображаючи origin — створюючи вразливість, описану вище.

Тестування на помилки конфігурації CORS: Надішли запит з довільним заголовком Origin і перевір, чи він відображається в Access-Control-Allow-Origin. Також протестуй з Origin: null. Якщо будь-який із них відображається з Allow-Credentials: true, додаток вразливий.
