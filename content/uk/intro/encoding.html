Модуль 03 — Кодування та криптографія

Кодування vs шифрування vs хешування

Ці три концепції часто плутають, але вони виконують принципово різні функції у веб-безпеці. Розуміння різниці між ними критично важливе, щоб розпізнавати, де дані можна повернути у вихідний вигляд, де потрібні ключі, а де результат є незворотним.

Властивість Кодування Шифрування Хешування
Призначення Представлення / передача даних Конфіденційність Цілісність / відбиток даних
Зворотне? Так, секрет не потрібен Так, за наявності правильного ключа Ні (одностороння функція)
Потрібен ключ? Ні Так Ні
Приклад Base64, URL encoding AES, XOR cipher SHA-256, MD5
Наслідки для безпеки: Кодування — це НЕ засіб захисту. Зловмисники легко декодують Base64 або URL-encoded дані. Ніколи не покладайся лише на кодування для захисту конфіденційних даних.

Base64

Base64 кодує бінарні дані в алфавіт із 64 ASCII-символів: A-Z, a-z, 0-9, +, /, а = використовується для доповнення. Кожні 3 байти вхідних даних перетворюються на 4 символи Base64. 

Input:   "Man"
ASCII:   77 97 110
Binary:  01001101 01100001 01101110
6-bit:   010011 010110 000101 101110
Base64:  T        W       F       u
Output:  "TWFu"

Доповнення (padding): Коли довжина вхідних даних не кратна 3, додаються символи =. Один байт вхідних даних дає два символи Base64 плюс ==; два байти — три символи плюс =. 

"M"   -> "TQ=="   (1 byte, pad with ==)
"Ma"  -> "TWE="   (2 bytes, pad with =)
"Man" -> "TWFu"   (3 bytes, no padding)

URL-safe варіант: Замінює + на - і / на _. Використовується у JWT, data URI та URL-параметрах, де + і / — зарезервовані символи.

Де ти зустрінеш Base64 на практиці: заголовки HTTP Basic Auth (Authorization: Basic dXNlcjpwYXNz), вкладення електронної пошти (MIME), data URI, JWT та cookies, що зберігають серіалізовані об'єкти.

URL Encoding (Percent-Encoding)

URL encoding замінює небезпечні ASCII-символи на % з двома шістнадцятковими цифрами, що відповідають байтовому значенню символу. Наприклад, пробіл стає %20, а < стає %3C. 

Input:    <script>alert(1)</script>
Encoded:  %3Cscript%3Ealert(1)%3C%2Fscript%3E

Подвійне кодування: Якщо WAF або фільтр декодує URL один раз, а потім додаток декодує ще раз, зловмисник може подвійно закодувати payload, щоб обійти фільтр: 

Original:        <
Single-encoded:  %3C
Double-encoded:  %253C   (the % itself becomes %25)
Техніка обходу: Подвійне URL encoding — поширений метод обходу вхідних фільтрів та WAF, які декодують лише один шар. Завжди повністю нормалізуй вхідні дані перед валідацією.

Hex Encoding

Кожен байт вхідних даних представляється двома шістнадцятковими символами (00-ff). Часто зустрічається в мережевих протоколах, аналізі бінарних файлів та низькорівневому дебагінгу. Рядок "ABC" стає 41 42 43.

HTML Entity Encoding

HTML-сутності представляють зарезервовані або спеціальні символи так, щоб браузери відображали їх як текст, а не інтерпретували як розмітку. Існують іменовані та числові сутності: 

&lt;    = <      (named entity)
&gt;    = >      (named entity)
&amp;   = &      (named entity)
&quot;  = "      (named entity)
&#60;   = <      (decimal numeric entity)
&#x3C;  = <      (hexadecimal numeric entity)
Значення для XSS: Якщо введені користувачем дані відображаються в HTML без entity encoding, зловмисник може впровадити теги <script>. Правильне HTML entity encoding — основний захист від reflected та stored XSS у HTML-контекстах.

Caesar Cipher / ROT13

Caesar cipher зсуває кожну літеру на фіксовану кількість позицій в алфавіті. ROT13 — це окремий випадок із зсувом на 13. Оскільки англійський алфавіт має 26 літер, подвійне застосування ROT13 повертає оригінальний текст — він є власною оберненою функцією. 

ROT13("Hello World") = "Uryyb Jbeyq"
ROT13("Uryyb Jbeyq") = "Hello World"

ROT13 не забезпечує жодної безпеки — це просто техніка обфускації, яку іноді використовують, щоб приховати спойлери або тривіально замаскувати рядки в CTF.

XOR Cipher

XOR (виключне АБО) шифрування комбінує відкритий текст із ключем, що повторюється, побайтово. Воно симетричне: шифрування та дешифрування використовують одну й ту саму операцію. XOR має важливі властивості:

  • A ^ 0 = A — XOR з нулем — тотожність
  • A ^ A = 0 — XOR із самим собою — нуль
  • A ^ B ^ B = A — подвійне застосування ключа відновлює відкритий текст
Plaintext:  "Hi"   -> 0x48 0x69
Key:        "K"    -> 0x4B 0x4B  (repeated)
XOR result:         -> 0x03 0x22
Hex output: "0322"
Слабкість: Однобайтовий або короткий XOR із ключем, що повторюється, тривіально зламується за допомогою частотного аналізу. Якщо ключ використовується повторно, C1 ^ C2 = P1 ^ P2, що витікає інформацію про обидва відкриті тексти.

Криптографічні хеш-функції: MD5, SHA-1, SHA-256

Криптографічна хеш-функція приймає вхідні дані довільної довжини та створює дайджест фіксованої довжини. Ключові властивості:

  • Односторонність: Маючи H(m), обчислювально неможливо знайти m
  • Детермінованість: Однакові вхідні дані завжди дають однаковий хеш
  • Лавинний ефект: Найменша зміна вхідних даних кардинально змінює результат
  • Стійкість до колізій: Важко знайти два різні входи з однаковим хешем
Алгоритм Довжина дайджесту Статус
MD5 128 біт (32 hex-символи) Зламаний — практичні атаки на колізії з 2004 року
SHA-1 160 біт (40 hex-символів) Застарілий — колізію продемонстровано (SHAttered, 2017)
SHA-256 256 біт (64 hex-символи) Безпечний — відомих практичних атак немає 
MD5("hello")    = 5d41402abc4b2a76b9719d911017c592
SHA-1("hello")  = aaf4c61ddcc5e8a2dabede0f3b482cd9aea9434d
SHA-256("hello")= 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824

JSON Web Tokens (JWT)

JWT складається з трьох частин, закодованих у Base64url та розділених крапками: header.payload.signature. Вони широко використовуються для автентифікації та управління сесіями в сучасних веб-додатках. 

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

Header:    {"alg":"HS256","typ":"JWT"}
Payload:   {"sub":"1234567890","name":"John Doe","iat":1516239022}
Signature: HMAC-SHA256(base64url(header) + "." + base64url(payload), secret)
Атака alg:none: Деякі бібліотеки JWT приймають "alg":"none" в заголовку, що означає «підпис не потрібен». Зловмисник може підробити будь-який payload, встановити алгоритм none, видалити підпис — і сервер прийме токен як валідний. 
// Malicious JWT header
{"alg":"none","typ":"JWT"}

// Forged payload — attacker escalates to admin
{"sub":"1","role":"admin","iat":1516239022}

// Token: base64url(header).base64url(payload).
// Note the trailing dot with an empty signature
Захист: Завжди перевіряй поле alg на стороні сервера за білим списком. Ніколи не приймай none як валідний алгоритм у продакшені. Використовуй бібліотеки, які за замовчуванням перевіряють алгоритм.
