Модуль 16 — Insecure Deserialization

Розберися, як ненадійні серіалізовані дані можуть призвести до віддаленого виконання коду через Python pickle, YAML та ін'єкцію кастомних об'єктів.

Найнедооціненіша вразливість

Вразливості десеріалізації — дивна штука, бо вони зовсім не схожі на інші вразливості. Тут немає точки ін'єкції у полі форми. Немає параметра URL, який можна підмінити. Натомість вектор атаки — це блоб бінарних або закодованих даних: кука, параметр API, завантажений файл — які додаток десеріалізує (перетворює з байтів назад у об'єкт) за допомогою небезпечного методу.

Наслідок? Remote Code Execution. Не "можливо" чи "за певних умов". Просто RCE. Атакуючий створює серіалізований об'єкт, який при десеріалізації виконує довільні команди на сервері. Без автентифікації, без SQL-запитів, без взаємодії з браузером — просто відправ пейлоад і отримай шелл.

Саме тому insecure deserialization є в OWASP Top 10 з 2017 року. Це не найпоширеніша вразливість, але коли ти її знаходиш — вплив майже завжди критичний.

Серіалізація 101

Почнемо з основ. Серіалізація перетворює об'єкт у пам'яті у формат, який можна зберегти або передати (байти, рядки, JSON). Десеріалізація робить зворотне — бере збережений формат і відтворює оригінальний об'єкт.

Кожна мова програмування має механізми серіалізації. Деякі безпечні (JSON — працює лише з базовими типами даних). Деякі неймовірно небезпечні (Python pickle, Java ObjectInputStream, PHP unserialize), бо вони можуть відтворювати довільні об'єкти, включаючи об'єкти, що виконують код під час своєї побудови.

Аналогія: Уяви, що ти отримуєш посилку поштою. Серіалізація через JSON — це коробка з кубиками LEGO — нешкідливі дані, які ти збираєш сам. Серіалізація через pickle — це повністю зібраний пристрій, який сам вмикається і починає працювати в момент відкриття коробки. Якби тобі надіслали бомбу, ти б точно не хотів формат посилки, що сам детонує при відкритті.

Python Pickle — класичний приклад

Модуль pickle у Python — це підручниковий приклад небезпечної десеріалізації. Він може серіалізувати і десеріалізувати будь-який об'єкт Python і використовує спеціальний метод __reduce__ для контролю того, як об'єкти відтворюються. Ключовий момент: __reduce__ може повертати будь-який callable, і цей callable викликається під час десеріалізації.

Вразливий код

import pickle, base64

@app.route('/load', methods=['POST'])
def load_data():
    data = request.form.get('data')
    # DANGEROUS: deserializes untrusted data
    # pickle.loads() will execute ANY code embedded in the payload
    obj = pickle.loads(base64.b64decode(data))
    return str(obj)

Експлойт

import pickle, base64, os

class Exploit:
    def __reduce__(self):
        # This method is called during deserialization
        # It returns a tuple: (callable, args)
        # pickle will call: os.popen('cat /etc/passwd')
        return (os.popen, ('cat /etc/passwd',))

payload = base64.b64encode(pickle.dumps(Exploit())).decode()
print(payload)  # Send this to the vulnerable endpoint

# When the server runs pickle.loads() on this payload,
# it calls os.popen('cat /etc/passwd') — RCE achieved.

Ось і все. П'ять рядків коду експлойта. Атакуючий створює об'єкт, метод __reduce__ якого повертає (os.popen, ('cat /etc/passwd',)). Коли pickle.loads() десеріалізує цей об'єкт, він викликає os.popen('cat /etc/passwd'). Сервер слухняно виконує команду і повертає результат. Гра закінчена.

Безпечна альтернатива

import json

@app.route('/load', methods=['POST'])
def load_data():
    data = request.form.get('data')
    # SAFE: JSON only handles basic types (strings, numbers, lists, dicts)
    # It CANNOT execute code during parsing — there is no __reduce__ equivalent
    obj = json.loads(data)
    return str(obj)
Документація Python прямо попереджає: В офіційній документації Python написано: "Warning: The pickle module is not secure. Only unpickle data you trust." Попри це попередження, розробники регулярно використовують pickle для десеріалізації даних від користувачів — у куках, параметрах API, чергах повідомлень та кеш-сховищах.

Десеріалізація YAML

Бібліотека YAML для Python має ту саму проблему. Функція yaml.unsafe_load() (та yaml.load() з певними лоадерами) може створювати довільні об'єкти Python із YAML-синтаксису: 

# DANGEROUS: yaml.unsafe_load() can execute code
import yaml
data = yaml.unsafe_load(user_input)
# Attack payload: !!python/object/apply:os.popen ['cat /etc/passwd']
# The !! syntax tells YAML to construct a Python object

# SAFE: yaml.safe_load() only allows basic types (strings, numbers, lists, dicts)
data = yaml.safe_load(user_input)

Java Deserialization — корпоративний кошмар

ObjectInputStream у Java має ту саму фундаментальну проблему, що й pickle у Python, але масштаб наслідків значно більший, тому що Java масово використовується в корпоративному софті. У 2015 році дослідники з Foxglove Security опублікували статтю, яка показала, що майже кожен великий Java-фреймворк (Apache Commons Collections, Spring, WebSphere, JBoss, WebLogic) містить "gadget chains" — послідовності об'єктів, які при десеріалізації зв'язуються в ланцюжок і виконують довільні команди.

Інструмент ysoserial автоматизує генерацію таких пейлоадів. Ти вказуєш цільову бібліотеку та команду, яку хочеш виконати, і він генерує серіалізований Java-об'єкт, що забезпечує RCE при десеріалізації.

Реальна історія — Злам Equifax (2017): Витік даних Equifax, що розкрив персональні дані 147 мільйонів американців (включаючи номери соціального страхування), був спричинений вразливістю десеріалізації в Apache Struts (CVE-2017-5638). Атакуючий відправив спеціально сформований заголовок Content-Type з OGNL-виразом, який був десеріалізований і виконаний на сервері. Equifax не встановлювала патч для відомої вразливості понад два місяці.

Десеріалізація через куки

Поширений патерн: додаток зберігає стан користувача у підписаній куці. Кука містить серіалізовані дані (часто base64-закодований pickle або серіалізовані PHP-об'єкти). Сервер підписує куку HMAC-підписом для захисту від підміни. Звучить безпечно, так?

Проблема: якщо ключ підпису слабкий або витік, атакуючий може підробити куку. Flask використовує сесійну куку, підписану SECRET_KEY додатка. Якщо цей ключ — щось типу "secret" чи "development", або залишений як дефолтний у фреймворку, інструменти на кшталт flask-unsign можуть його зламати і підробити куки з довільними даними — включаючи pickle-пейлоади. 

# Crack a Flask session cookie's signing key
flask-unsign --unsign --cookie "eyJ..." --wordlist rockyou.txt

# Forge a new cookie with a malicious payload
flask-unsign --sign --cookie '{"admin": true}' --secret 'cracked-key'
Захист: Правила прості: (1) Ніколи не десеріалізуй ненадійні дані через pickle, yaml.unsafe_load, Java ObjectInputStream, PHP unserialize або будь-який формат, що може створювати довільні об'єкти. (2) Використовуй JSON для обміну даними — він працює лише з примітивними типами і не може виконувати код. (3) Якщо тобі необхідні підписані куки, використовуй сильний, випадковий SECRET_KEY (мінімум 32 байти ентропії). (4) Оновлюй фреймворки — нові gadget chains для десеріалізації знаходять регулярно.
