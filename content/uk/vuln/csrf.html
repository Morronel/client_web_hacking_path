Модуль 17 — Cross-Site Request Forgery (CSRF)

Розберися, як атакуючі змушують автентифікованих користувачів виконувати небажані дії, експлуатуючи автоматичне прикріплення кук браузером.

Збитий з пантелику помічник

CSRF — одна з найелегантніших атак у веб-безпеці, бо вона експлуатує не баг у коді, а фундаментальний принцип роботи браузерів. Суть проблеми: коли твій браузер робить запит до bank.com, він автоматично прикріплює всі куки для bank.com, включаючи твою сесійну куку. Браузер робить це незалежно від того, звідки прийшов запит.

Тобто якщо ти залогінений у свій банк і заходиш на зловмисний сайт, цей сайт може змусити твій браузер відправити запит на bank.com/transfer?to=attacker&amount=10000 — і браузер люб'язно прикріпить твою сесійну куку, зробивши запит нерозрізненним від легітимного.

Сервер банку бачить валідну сесійну куку і обробляє переказ. Він не може дізнатися, що запит прийшов з evil.com, а не зі сторінки самого банку. Браузер виступає "збитим з пантелику помічником" — він має повноваження діяти від твого імені (через сесійну куку), але його обманом змушують використовувати ці повноваження на користь атакуючого.

Хід атаки, крок за кроком

  1. Жертва логіниться на bank.com і отримує сесійну куку (session=abc123).
  2. Жертва заходить на evil.com (за посиланням з листа, поста на форумі, реклами тощо), залишаючись залогіненою в банку.
  3. evil.com містить приховану форму, що автоматично відправляється POST-запитом на bank.com/transfer.
  4. Браузер жертви відправляє форму. Оскільки ціль — bank.com, браузер прикріплює куку session=abc123.
  5. Сервер банку бачить валідну сесію та валідний запит на переказ. Він обробляє переказ. Жертва нічого не бачить — відправка форми відбулася автоматично і непомітно.
<!-- The attacker's page (evil.com) -->
<html>
<body onload="document.forms[0].submit()">
  <form method="POST" action="https://bank.com/transfer">
    <input type="hidden" name="to" value="attacker-account">
    <input type="hidden" name="amount" value="10000">
  </form>
</body>
</html>
Чому це працює? Same-Origin Policy не дозволяє JavaScript на evil.com читати відповіді з bank.com. Але вона НЕ забороняє міжсайтові відправки форм, завантаження зображень чи скриптів. Атакуючому не потрібно читати відповідь — побічний ефект (переказ грошей) і є метою.

Вразливий код

# Flask — VULNERABLE: no CSRF token validation
@app.route('/transfer', methods=['POST'])
@login_required
def transfer():
    to_account = request.form['to']
    amount = request.form['amount']
    # The server trusts the request because the session cookie is valid
    # But it never verifies that the request came from the bank's own page
    db.execute("UPDATE accounts SET balance = balance - ? WHERE user_id = ?",
               (amount, current_user.id))
    db.execute("UPDATE accounts SET balance = balance + ? WHERE user_id = ?",
               (amount, to_account))
    db.commit()
    return redirect('/dashboard')

Захист #1: CSRF-токени

Найпоширеніший захист. Сервер генерує випадковий, непередбачуваний токен і вставляє його в кожну форму як приховане поле. При відправці форми сервер перевіряє, що токен присутній і правильний. Оскільки атакуючий не може прочитати сторінки банку (SOP це блокує), він не може отримати токен, тому його підроблена форма буде без токена і буде відхилена. 

# Flask — SAFE: CSRF token required
from flask_wtf import FlaskForm, CSRFProtect
from wtforms import StringField, DecimalField

csrf = CSRFProtect(app)

class TransferForm(FlaskForm):
    to = StringField('Recipient')
    amount = DecimalField('Amount')

@app.route('/transfer', methods=['POST'])
@login_required
def transfer():
    form = TransferForm()
    if form.validate_on_submit():  # validates CSRF token automatically
        # process transfer — token is valid, request is genuine
        pass
    return redirect('/dashboard')
<!-- Template includes hidden CSRF token -->
<form method="POST" action="/transfer">
  {{ form.hidden_tag() }}  <!-- renders: <input type="hidden" name="csrf_token" value="random-token-here"> -->
  <input name="to" placeholder="Recipient">
  <input name="amount" placeholder="Amount">
  <button type="submit">Transfer</button>
</form>

Захист #2: SameSite куки

Атрибут SameSite для кук — це захист на рівні браузера, що контролює, чи відправляються куки з міжсайтовими запитами. Це, мабуть, найбільше покращення у захисті від CSRF за останнє десятиліття.

  • Strict: кука НІКОЛИ не відправляється з міжсайтовими запитами. Максимальний захист, але може зламати легітимні сценарії (наприклад, перехід за посиланням на сайт з листа — сесійна кука не буде відправлена, і користувач виглядатиме як незалогінений).
  • Lax: кука відправляється при навігації верхнього рівня через GET (клік по посиланню), але НЕ при POST-формах, iframe чи AJAX-запитах з інших сайтів. Це дефолт у сучасних браузерах (Chrome, Firefox, Edge) і забезпечує непоганий захист від CSRF для ендпоінтів, що змінюють стан через POST.
  • None: кука завжди відправляється міжсайтово (вимагає прапорець Secure). Жодного захисту від CSRF. Використовуй лише для кук, які явно мають працювати міжсайтово (наприклад, OAuth, вбудовані віджети).
Хороші новини: З 2020 року Chrome, Firefox та Edge за замовчуванням встановлюють кукам SameSite=Lax, якщо атрибут SameSite не вказано. Це означає, що більшість нових веб-додатків отримують базовий захист від CSRF "безкоштовно". Проте все одно варто реалізувати CSRF-токени як додатковий рівень захисту, бо Lax не захищає від зміни стану через GET, а старіші браузери можуть не підтримувати SameSite.

Захист #3: Валідація Origin/Referer

Сервер може перевіряти HTTP-заголовки Origin або Referer, щоб переконатися, що запит прийшов з того самого сайту. Це корисний допоміжний захист, але він не повинен бути єдиним, бо:

  • Розширення для приватності можуть видаляти заголовок Referer
  • Деякі проксі та фаєрволи змінюють або видаляють заголовки Origin
  • Редиректи через meta-refresh можуть обійти перевірку Referer

JSON API та CSRF

Поширена помилка: "Мій API приймає тільки JSON, тому він не вразливий до CSRF, бо HTML-форми не можуть відправляти JSON." Це переважно правда в сучасних браузерах з SameSite=Lax, але є нюанси:

  • Якщо сервер приймає Content-Type: text/plain і парсить тіло як JSON, форма може відправити enctype="text/plain" зі спеціально сформованим тілом
  • navigator.sendBeacon() може відправляти довільні content types у деяких конфігураціях
  • Якщо на сесійній куці встановлено SameSite=None, fetch() з credentials: 'include' може відправляти JSON міжсайтово (хоча сервер також повинен мати дозвільні CORS-заголовки)
Найкраща практика: Для JSON API вимагай кастомний заголовок, наприклад X-Requested-With: XMLHttpRequest. Кастомні заголовки не можуть бути встановлені HTML-формами, тому їхня наявність доводить, що запит прийшов від JavaScript на твоєму сайті (або сайті, дозволеному твоєю CORS-політикою). Іноді це називають патерном "double-submit" для API.
Вплив CSRF: Захоплення акаунта (зміна email або пароля жертви), несанкціоновані грошові перекази, ескалація привілеїв (жертва додає атакуючого як адміна), зміна даних (видалення ресурсів, зміна налаштувань) та посилення соціальної інженерії (жертва публікує контент, який не писала).
