Модуль 21 — Вразливості GraphQL

Дізнайся, як GraphQL API створюють унікальні поверхні атак, включаючи витоки через introspection, атаки глибиною запитів, ін'єкції та обхід авторизації.

Інший тип API — інший тип атак

GraphQL розробили у Facebook у 2012 році та зробили open-source у 2015. Він вирішує реальну проблему REST API: надмірне або недостатнє завантаження даних. Замість того, щоб робити запити на кілька REST-ендпоінтів і отримувати фіксовані формати відповідей, клієнт відправляє один запит, де точно вказує, які дані йому потрібні, і сервер повертає саме це.

Ця потужність має свою ціну. GraphQL створює поверхні атак, яких просто не існує в REST:

  • Один ендпоінт обробляє всі операції — правила WAF, розраховані на REST-шляхи, не працюють
  • Introspection розкриває всю схему будь-кому, хто запитає
  • Клієнти контролюють глибину та складність запитів, що дозволяє DoS-атаки
  • Авторизацію потрібно перевіряти для кожного поля в кожному резолвері, а не просто для кожного ендпоінта
  • Batching дозволяє атакуючим відправляти тисячі операцій в одному HTTP-запиті

Якщо ти зустрінеш ендпоінт /graphql під час пентесту або баг-баунті, зверни на нього особливу увагу. GraphQL API часто неправильно налаштовані, і вразливості можуть бути серйозними.

Основи GraphQL (швидкий вступ)

# Query — read data (like GET in REST)
{
  users {
    id
    username
    email
    posts {
      title
    }
  }
}

# Mutation — modify data (like POST/PUT/DELETE in REST)
mutation {
  createPost(title: "Hello", content: "World") {
    id
    createdAt
  }
}

# The response mirrors the query structure:
# { "data": { "users": [{ "id": 1, "username": "alice", "email": "...", "posts": [...] }] } }

Атака #1: Introspection — схема як на долоні

GraphQL має вбудовану функцію introspection, яка дозволяє будь-якому клієнту запитати повну схему — кожен тип, кожне поле, кожен зв'язок, кожну мутацію. Це неймовірно корисно під час розробки. Це також неймовірно корисно для атакуючих. 

# The introspection query — reveals EVERYTHING
{
  __schema {
    types {
      name
      fields {
        name
        type { name kind }
      }
    }
  }
}

# Find all queries and mutations
{
  __schema {
    queryType { fields { name } }
    mutationType { fields { name } }
  }
}

Коли ти запускаєш це проти неправильно налаштованого production API, ти можеш виявити типи на кшталт AdminUser, InternalConfig, DebugLog або мутації типу deleteUser, promoteToAdmin, resetPassword. Схема — це, по суті, карта всього API, включаючи частини, про які розробники думали, що їх ніхто не знайде.

Інструменти: Використовуй GraphQL Voyager для візуалізації схеми як інтерактивного графа, або InQL (розширення для Burp Suite) для автоматичного витягування та аналізу GraphQL-схем. Для тестування з командного рядка graphql-cop виконує автоматичні перевірки безпеки GraphQL-ендпоінтів.

Атака #2: DoS через глибину та складність

Зв'язки GraphQL можна вкладати рекурсивно. Якщо User має posts, а Post має author, їх можна вкладати нескінченно: 

# This query is exponentially expensive
{
  users {
    posts {
      author {
        posts {
          author {
            posts {
              author {
                # ... keeps going — each level multiplies the work
              }
            }
          }
        }
      }
    }
  }
}

Без обмеження глибини цей запит може спожити величезну кількість серверних ресурсів — CPU, пам'яті та з'єднань з базою даних. Один зловмисний запит може покласти весь API. Це атака Denial of Service (DoS), унікальна для GraphQL.

Атака #3: Обхід авторизації

У REST авторизація часто перевіряється на рівні ендпоінта: "тільки адміни мають доступ до /api/admin/users." У GraphQL є лише один ендпоінт. Авторизацію потрібно перевіряти в кожному резолвері, для кожного поля. 

# DANGEROUS: no auth check — returns ALL posts including private ones
def resolve_posts(root, info):
    return db.execute('SELECT * FROM posts').fetchall()

# SAFE: filter by current user's permissions
def resolve_posts(root, info):
    user = info.context['user']
    if user.is_admin:
        return db.execute('SELECT * FROM posts').fetchall()
    return db.execute('SELECT * FROM posts WHERE author_id=? OR public=1',
                      (user.id,)).fetchall()

Типові помилки: захистити мутацію типу deleteUser, але не відповідний запит, що розкриває дані користувачів, або захистити ресурс по одному шляху запиту (user.privateEmail), але не по іншому (post.author.privateEmail).

Атака #4: SQL Injection через резолвери

GraphQL магічно не запобігає ін'єкціям. Якщо резолвер будує SQL-запити конкатенацією аргументів від користувача, він вразливий до тієї самої SQL injection, що й будь-який інший додаток: 

# DANGEROUS: string interpolation in resolver
def resolve_search_users(root, info, name):
    return db.execute(
        f"SELECT * FROM users WHERE name LIKE '%{name}%'"
    ).fetchall()
    # GraphQL query: { searchUsers(name: "' UNION SELECT * FROM secrets--") { ... } }
    # → SQL injection!

Атака #5: Batching та брутфорс

Багато GraphQL-серверів приймають масиви запитів в одному HTTP-запиті. Це дозволяє:

  • Обхід rate limiting: відправити 1 000 спроб логіну в одному HTTP-запиті — якщо rate limiter рахує HTTP-запити, він бачить лише один
  • Прискорення брутфорсу: перебрати тисячі паролів, OTP-кодів або API-ключів пачкою
// Single HTTP request, 100 login attempts
[
  { "query": "mutation { login(email: \"admin@x.com\", pass: \"pass1\") { token } }" },
  { "query": "mutation { login(email: \"admin@x.com\", pass: \"pass2\") { token } }" },
  { "query": "mutation { login(email: \"admin@x.com\", pass: \"pass3\") { token } }" }
  // ... 97 more
]

Атака #6: Витоки через підказки полів

Навіть коли introspection вимкнений, багато реалізацій GraphQL підказують правильні назви полів, коли ти допускаєш помилку. Запитай { users { passwor } } — і помилка може сказати: "Did you mean 'password' or 'passwordHash'?" Це витік інформації про схему через чорний хід.

Чеклист захисту

  • Вимкни introspection у production — у більшості фреймворків це один рядок конфігурації
  • Реалізуй обмеження глибини запитів — обмеж до 5-10 рівнів
  • Аналіз вартості запитів — присвоюй вагу полям і відхиляй запити, що перевищують бюджет
  • Авторизація на рівні полів у кожному резолвері — ніколи не вважай поле "прихованим"
  • Параметризовані запити в резолверах — ті самі правила, що й для будь-якого SQL-коду
  • Обмеження розміру batch — обмеж масиви запитів до 10-20 операцій
  • Rate limiting на операцію, а не лише на HTTP-запит
  • Вимкни підказки полів у повідомленнях про помилки для production
Вплив: Вразливості GraphQL можуть розкрити всю схему бази даних, викрити приватні дані через прогалини в авторизації, забезпечити DoS через дорогі запити, слугувати вектором ін'єкцій через небезпечні резолвери та обходити rate limiting через batching. Архітектура з одним ендпоінтом означає, що традиційні правила WAF та API-шлюзи часто пропускають ці атаки повністю.
