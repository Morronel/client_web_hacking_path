Обфускація та обхід WAF

Гра в кота і мишку

Уяви: ти знайшов SQL injection вразливість. Формуєш пейлоад, відправляєш запит, і... сервер повертає 403 Forbidden. Твій пейлоад заблоковано. Не самим додатком, а Web Application Firewall (WAF), який стоїть перед ним і перевіряє кожен запит на наявність чогось підозрілого.

Обхід WAF — один із найкреативніших аспектів наступальної безпеки. Це постійна гонка озброєнь: вендори WAF додають нові правила виявлення, дослідники знаходять способи їх обійти, вендори оновлюють правила, дослідники знаходять нові обходи. Розуміння обходу WAF є критично важливим для пентестерів (бо реальні цілі мають WAF) та для захисників (бо знання того, як WAF можна обійти, допомагає не покладатися на нього як єдиний засіб захисту).

Що таке WAF?

Web Application Firewall (WAF) — це рівень безпеки, який стоїть між користувачами та веб-додатком, перевіряючи HTTP-трафік і блокуючи запити, які відповідають відомим шаблонам атак. Організації розгортають WAF, щоб додати рівень захисту від поширених веб-атак на кшталт SQL injection, XSS та command injection.

Серед популярних WAF — Cloudflare, AWS WAF, ModSecurity, Imperva та Akamai. Хоча вони є цінними інструментами захисту, вони не замінюють написання безпечного коду. WAF — це пластир, а не ліки. Якщо основна вразливість існує, достатньо кваліфікований зловмисник знайде спосіб обійти WAF.

Виявлення на основі сигнатур

Більшість WAF значною мірою покладаються на виявлення на основі сигнатур — вони підтримують базу даних шаблонів (регулярні вирази, збіги рядків), що відповідають відомим пейлоадам атак. Коли вхідний запит збігається із сигнатурою, WAF його блокує. 

Example WAF rules (simplified):
  Block if request contains: <script
  Block if request contains: ' OR 1=1
  Block if request contains: UNION SELECT
  Block if request contains: /etc/passwd

Фундаментальна слабкість виявлення на основі сигнатур полягає в тому, що воно може зловити лише те, про що знає. Трансформуючи синтаксис пейлоаду без зміни його семантики, зловмисник може обійти сигнатури.

Поширені техніки обходу

1. Варіація регістру

Багато фільтрів відповідають конкретному регістру. Оскільки HTML та SQL здебільшого нечутливі до регістру, змішування регістру може обійти примітивні фільтри: 

Blocked:  <script>alert(1)</script>
Bypass:   <ScRiPt>alert(1)</ScRiPt>

Blocked:  UNION SELECT
Bypass:   uNiOn SeLeCt

2. URL-кодування

Кодування символів у їх відсоткові еквіваленти. Якщо WAF перевіряє до того, як сервер декодує, пейлоад проскакує: 

Blocked:  <script>
Encoded:  %3Cscript%3E

3. Кодування HTML-сутностями

У HTML-контексті символи, закодовані сутностями, декодуються браузером: 

Blocked:  <img src=x onerror=alert(1)>
Encoded:  <img src=x onerror=alert(1)>

4. Вставка SQL-коментарів

SQL дозволяє вбудовані коментарі (/*...*/) всюди, де допустимі пробіли. Вставка коментарів розбиває ключові слова, які шукає WAF: 

Blocked:  UNION SELECT * FROM users
Bypass:   UN/**/ION SEL/**/ECT * FROM users

5. Подвійне кодування

Якщо WAF декодує один раз, а потім передає запит додатку, який декодує повторно, подвійне кодування може обійти фільтр: 

Original:        <
Single encoded:  %3C
Double encoded:  %253C  (the % is encoded as %25)

6. Нормалізація Unicode

Деякі додатки нормалізують символи Unicode до їх ASCII-еквівалентів після перевірки WAF. Використання Unicode-двійників може обійти фільтри: 

Normal:    <script>
Unicode:   ＜script＞  (using fullwidth characters)
Етичний контекст: Техніки обходу WAF слід використовувати лише під час авторизованого pentest або bug bounty програм, де ти маєш явний дозвіл. Використання цих технік проти систем, які тобі не належать і на тестування яких у тебе немає дозволу, є незаконним та неетичним.
Перспектива захисту: Розуміння технік обходу є критично важливим для побудови кращого захисту. Розробники не повинні покладатися лише на WAF — завжди валідуй та санітизуй вхідні дані на рівні додатку, використовуй параметризовані запити та впроваджуй Content Security Policy.
