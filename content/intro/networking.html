Module 02 — Networking & Protocols

Understand the protocols that power the web and the security boundaries they create.

Speaking the Web's Language

Before you can hack a web application, you need to understand how a web application actually works. And at its core, every web application is just a conversation between two computers — your browser (the client) and a server somewhere in the world. This conversation happens using protocols: agreed-upon languages and rules that both sides understand.

If you have ever used Burp Suite or looked at the Network tab in your browser's developer tools, you have already seen these protocols in action. Every time you click a link, submit a form, or load an image, your browser sends an HTTP request and receives an HTTP response. Understanding the anatomy of these requests is not optional for a web hacker — it is the foundation of everything.

A penetration tester who does not understand HTTP is like a locksmith who does not understand how locks work. Sure, you might get lucky with a few tools, but you will never truly understand what you are doing or why it works.

8a. HTTP — HyperText Transfer Protocol

HTTP is a request/response protocol. The client sends a request; the server sends a response. Every web interaction — loading a page, submitting a form, calling an API — follows this pattern.

Request Anatomy

GET /api/users?page=1 HTTP/1.1
Host: example.com
Accept: application/json
Authorization: Bearer eyJhbGc...
Cookie: session=abc123

Response Anatomy

HTTP/1.1 200 OK
Content-Type: application/json
Set-Cookie: session=abc123; HttpOnly; Secure
X-Frame-Options: DENY

{"users": [...]}

8b. TCP & TLS

TCP Three-Way Handshake

Before any HTTP data flows, TCP establishes a connection:

  1. SYN: Client sends synchronization request with sequence number
  2. SYN-ACK: Server acknowledges and sends its own sequence number
  3. ACK: Client acknowledges — connection established

TLS Handshake

Built on top of TCP, TLS encrypts the connection:

  1. ClientHello: Supported cipher suites, TLS version, random data
  2. ServerHello: Chosen cipher suite, server certificate
  3. Key Exchange: Both sides derive the symmetric session key
  4. Finished: Both sides verify, encrypted communication begins
Why HTTPS matters: Without TLS, all HTTP data (credentials, cookies, personal info) travels in plaintext, visible to anyone on the network path.

8c. DNS — Domain Name System

DNS translates domain names to IP addresses through a hierarchical resolution chain:

  1. Browser cache → checked first
  2. OS cache → /etc/hosts or OS resolver cache
  3. Recursive resolver → ISP or configured DNS (8.8.8.8)
  4. Root nameserver → directs to TLD server
  5. TLD nameserver → directs to authoritative server
  6. Authoritative nameserver → returns the actual IP

8d. Same-Origin Policy

The Same-Origin Policy (SOP) is the browser's core security model. Two URLs have the same origin if and only if they share the same scheme, host, and port.

https://example.com:443/path
  ↑         ↑           ↑
scheme    host        port

SOP blocks cross-origin reads (JavaScript on origin A cannot read responses from origin B). CORS is an opt-in mechanism for servers to relax this restriction.

8e. CIDR & Subnetting

CIDR (Classless Inter-Domain Routing) notation represents an IP address and its network mask: 192.168.1.0/24 means the first 24 bits are the network portion.
