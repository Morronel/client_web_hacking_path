Same-Origin Policy & CORS

What Is the Same-Origin Policy?

The Same-Origin Policy (SOP) is the most fundamental security mechanism in web browsers. It restricts how scripts loaded from one origin can interact with resources from another origin. Without SOP, any website you visit could read your email, access your bank account, and steal your session cookies from every other site you are logged into.

Defining "Origin"

An origin is defined by three components: scheme (protocol), host (domain), and port. Two URLs have the same origin if and only if all three match exactly.

URL A URL B Same Origin? Reason
https://example.com/page1 https://example.com/page2 Yes Same scheme, host, and port (443)
https://example.com http://example.com No Different scheme (https vs http)
https://example.com https://api.example.com No Different host (subdomain counts)
https://example.com https://example.com:8443 No Different port (443 vs 8443)
http://example.com:80 http://example.com Yes Port 80 is the default for http

What SOP Blocks and Allows

Cross-origin reads (BLOCKED by default)

JavaScript on evil.com cannot read the response from a fetch() or XMLHttpRequest to bank.com. The browser sends the request, but blocks the script from reading the response. This prevents data theft.

Cross-origin writes (ALLOWED)

Forms can submit POST requests to any origin. Links navigate to any origin. This is why CSRF (Cross-Site Request Forgery) attacks are possible — the browser happily sends the request along with cookies; it just does not let the attacker read the response.

Cross-origin embedding (ALLOWED)

Resources like <img>, <script>, <link>, <iframe>, and <video> can be loaded from any origin. This is how CDNs work — you load jQuery from cdn.jsdelivr.net even though your site is on a different origin. However, the embedding page cannot read the pixel data of a cross-origin image on a canvas (tainted canvas).

SOP does not prevent requests, it prevents reading responses. The server still receives and processes the cross-origin request. This distinction is crucial for understanding CSRF and why CORS was created.

CORS — Cross-Origin Resource Sharing

CORS is a mechanism that allows servers to selectively relax the Same-Origin Policy. When a web app on frontend.com needs to call an API on api.backend.com, the server can include CORS headers to tell the browser "it is okay to let this origin read my response."

Simple Requests

For simple requests (GET, HEAD, POST with standard content types), the browser sends the request directly and checks the response headers: 

Access-Control-Allow-Origin: https://frontend.com

If the header matches the requesting origin, the browser allows the script to read the response.

Preflight Requests

For "non-simple" requests (PUT, DELETE, custom headers, JSON content type), the browser first sends an OPTIONS request (the "preflight") to ask for permission: 

OPTIONS /api/data HTTP/1.1
Host: api.backend.com
Origin: https://frontend.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: Content-Type, Authorization

The server responds with allowed methods and headers:

Access-Control-Allow-Origin: https://frontend.com
Access-Control-Allow-Methods: GET, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 86400

Credentials and CORS

By default, cross-origin requests do not include cookies or HTTP authentication. To include them, the client must set credentials: 'include' (fetch) or withCredentials = true (XHR), and the server must respond with: 

Access-Control-Allow-Credentials: true

Critical rule: When Allow-Credentials: true, the Access-Control-Allow-Origin header CANNOT be the wildcard *. It must specify the exact origin. Browsers enforce this.

CORS Misconfigurations

CORS misconfigurations are a common source of vulnerabilities. Here are the most dangerous patterns:

1. Origin Reflection

The server blindly reflects the Origin header in Access-Control-Allow-Origin. Any website can now read authenticated responses: 

// Request from evil.com
Origin: https://evil.com

// Server response (vulnerable)
Access-Control-Allow-Origin: https://evil.com
Access-Control-Allow-Credentials: true

2. Null Origin Allowed

Some servers allow the null origin, thinking it is safe. But sandboxed iframes and local file pages send Origin: null, making exploitation trivial: 

Access-Control-Allow-Origin: null
Access-Control-Allow-Credentials: true

3. Wildcard with Credentials (Blocked by Browsers)

While Access-Control-Allow-Origin: * with Access-Control-Allow-Credentials: true is rejected by browsers, some developers work around this by reflecting the origin — creating the vulnerability described above.

Testing for CORS misconfiguration: Send a request with an arbitrary Origin header and check if it is reflected in Access-Control-Allow-Origin. Also test with Origin: null. If either is reflected with Allow-Credentials: true, the application is vulnerable.
