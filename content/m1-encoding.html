Module 01 — Encoding & Cryptography

Encoding vs Encryption vs Hashing

These three concepts are often confused, but they serve fundamentally different purposes in web security. Understanding the distinction is critical for recognizing where data can be reversed, where keys are required, and where output is irreversible.

Property Encoding Encryption Hashing
Purpose Data representation / transport Confidentiality Integrity / fingerprinting
Reversible? Yes, no secret needed Yes, with the correct key No (one-way function)
Key required? No Yes No
Example Base64, URL encoding AES, XOR cipher SHA-256, MD5
Security implication: Encoding is NOT a security measure. Attackers frequently decode Base64 or URL-encoded payloads. Never rely on encoding alone to protect sensitive data.

Base64

Base64 encodes binary data into a 64-character ASCII alphabet: A-Z, a-z, 0-9, +, /, with = used for padding. Every 3 bytes of input become 4 Base64 characters. 

Input:   "Man"
ASCII:   77 97 110
Binary:  01001101 01100001 01101110
6-bit:   010011 010110 000101 101110
Base64:  T        W       F       u
Output:  "TWFu"

Padding: When the input length is not a multiple of 3, = characters are appended. One byte of input produces two Base64 characters plus ==; two bytes produce three characters plus =. 

"M"   -> "TQ=="   (1 byte, pad with ==)
"Ma"  -> "TWE="   (2 bytes, pad with =)
"Man" -> "TWFu"   (3 bytes, no padding)

URL-safe variant: Replaces + with - and / with _. Used in JWTs, data URIs, and URL parameters where + and / are reserved characters.

Where you see Base64 in the wild: HTTP Basic Auth headers (Authorization: Basic dXNlcjpwYXNz), email attachments (MIME), data URIs, JWTs, and cookies storing serialized objects.

URL Encoding (Percent-Encoding)

URL encoding replaces unsafe ASCII characters with a % followed by two hexadecimal digits representing the character's byte value. For example, a space becomes %20 and < becomes %3C. 

Input:    <script>alert(1)</script>
Encoded:  %3Cscript%3Ealert(1)%3C%2Fscript%3E

Double encoding: If a WAF or filter URL-decodes once and then the application decodes again, an attacker can double-encode a payload to slip past the filter: 

Original:        <
Single-encoded:  %3C
Double-encoded:  %253C   (the % itself becomes %25)
Bypass technique: Double URL encoding is a common method for evading input filters and WAFs that only decode one layer. Always normalize input fully before validation.

Hex Encoding

Each byte of input is represented as two hexadecimal characters (00-ff). Common in network protocols, binary file analysis, and low-level debugging. The string "ABC" becomes 41 42 43.

HTML Entity Encoding

HTML entities represent reserved or special characters so that browsers render them as text rather than interpreting them as markup. There are named entities and numeric entities: 

&lt;    = <      (named entity)
&gt;    = >      (named entity)
&amp;   = &      (named entity)
&quot;  = "      (named entity)
&#60;   = <      (decimal numeric entity)
&#x3C;  = <      (hexadecimal numeric entity)
XSS relevance: If user input is reflected in HTML without entity encoding, an attacker can inject <script> tags. Proper HTML entity encoding is the primary defense against reflected and stored XSS in HTML contexts.

Caesar Cipher / ROT13

The Caesar cipher shifts each letter by a fixed number of positions in the alphabet. ROT13 is the specific case where the shift is 13. Since the English alphabet has 26 letters, applying ROT13 twice returns the original text — it is its own inverse. 

ROT13("Hello World") = "Uryyb Jbeyq"
ROT13("Uryyb Jbeyq") = "Hello World"

ROT13 provides zero security — it is simply an obfuscation technique sometimes used to hide spoilers or trivially obscure strings in CTFs.

XOR Cipher

XOR (exclusive or) encryption combines plaintext with a repeating key byte-by-byte. It is symmetric: encrypting and decrypting use the same operation. XOR has important properties:

  • A ^ 0 = A — XOR with zero is identity
  • A ^ A = 0 — XOR with itself is zero
  • A ^ B ^ B = A — applying the key twice recovers plaintext
Plaintext:  "Hi"   -> 0x48 0x69
Key:        "K"    -> 0x4B 0x4B  (repeated)
XOR result:         -> 0x03 0x22
Hex output: "0322"
Weakness: Single-byte or short repeating-key XOR is trivially breakable with frequency analysis. If the key is reused, C1 ^ C2 = P1 ^ P2, leaking information about both plaintexts.

Cryptographic Hash Functions: MD5, SHA-1, SHA-256

A cryptographic hash function takes arbitrary-length input and produces a fixed-length digest. Key properties:

  • One-way: Given H(m), it is computationally infeasible to find m
  • Deterministic: Same input always produces the same hash
  • Avalanche effect: A tiny change in input drastically changes the output
  • Collision resistance: Hard to find two different inputs with the same hash
Algorithm Digest Length Status
MD5 128 bits (32 hex chars) Broken — practical collision attacks since 2004
SHA-1 160 bits (40 hex chars) Deprecated — collision demonstrated (SHAttered, 2017)
SHA-256 256 bits (64 hex chars) Secure — no known practical attacks 
MD5("hello")    = 5d41402abc4b2a76b9719d911017c592
SHA-1("hello")  = aaf4c61ddcc5e8a2dabede0f3b482cd9aea9434d
SHA-256("hello")= 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824

JSON Web Tokens (JWT)

A JWT consists of three Base64url-encoded parts separated by dots: header.payload.signature. They are widely used for authentication and session management in modern web applications. 

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

Header:    {"alg":"HS256","typ":"JWT"}
Payload:   {"sub":"1234567890","name":"John Doe","iat":1516239022}
Signature: HMAC-SHA256(base64url(header) + "." + base64url(payload), secret)
The alg:none attack: Some JWT libraries accept "alg":"none" in the header, which means "no signature required." An attacker can forge any payload, set the algorithm to none, strip the signature, and the server accepts the token as valid. 
// Malicious JWT header
{"alg":"none","typ":"JWT"}

// Forged payload — attacker escalates to admin
{"sub":"1","role":"admin","iat":1516239022}

// Token: base64url(header).base64url(payload).
// Note the trailing dot with an empty signature
Mitigation: Always validate the alg field server-side against an allowlist. Never accept none as a valid algorithm in production. Use libraries that enforce algorithm verification by default.
