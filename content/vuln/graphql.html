Module 21 — GraphQL Vulnerabilities

Learn how GraphQL APIs introduce unique attack surfaces including introspection leaks, depth attacks, injection, and authorization bypasses.

A Different Kind of API, A Different Kind of Attack

GraphQL was developed by Facebook in 2012 and open-sourced in 2015. It solves a real problem with REST APIs: over-fetching and under-fetching data. Instead of hitting multiple REST endpoints and getting fixed response shapes, the client sends a single query specifying exactly what data it needs, and the server returns exactly that.

This power comes at a cost. GraphQL introduces attack surfaces that simply do not exist in REST:

  • A single endpoint handles all operations — WAF rules designed for REST paths do not work
  • Introspection reveals the entire schema to anyone who asks
  • Clients control query depth and complexity, enabling DoS attacks
  • Authorization must be enforced per-field in every resolver, not just per-endpoint
  • Batching lets attackers send thousands of operations in a single HTTP request

If you encounter a /graphql endpoint during a pentest or bug bounty, pay close attention. GraphQL APIs are commonly misconfigured, and the vulnerabilities can be severe.

GraphQL Fundamentals (Quick Primer)

# Query — read data (like GET in REST)
{
  users {
    id
    username
    email
    posts {
      title
    }
  }
}

# Mutation — modify data (like POST/PUT/DELETE in REST)
mutation {
  createPost(title: "Hello", content: "World") {
    id
    createdAt
  }
}

# The response mirrors the query structure:
# { "data": { "users": [{ "id": 1, "username": "alice", "email": "...", "posts": [...] }] } }

Attack #1: Introspection — The Schema Giveaway

GraphQL has a built-in feature called introspection that allows any client to query the complete schema — every type, every field, every relationship, every mutation. This is incredibly useful during development. It is also incredibly useful for attackers. 

# The introspection query — reveals EVERYTHING
{
  __schema {
    types {
      name
      fields {
        name
        type { name kind }
      }
    }
  }
}

# Find all queries and mutations
{
  __schema {
    queryType { fields { name } }
    mutationType { fields { name } }
  }
}

When you run this against a misconfigured production API, you might discover types like AdminUser, InternalConfig, DebugLog, or mutations like deleteUser, promoteToAdmin, resetPassword. The schema is essentially a roadmap of the entire API — including parts the developers assumed nobody would find.

Tools: Use GraphQL Voyager to visualize the schema as an interactive graph, or InQL (Burp Suite extension) to automatically extract and analyze GraphQL schemas. For CLI testing, graphql-cop performs automated security checks against GraphQL endpoints.

Attack #2: Depth and Complexity DoS

GraphQL relationships can be nested recursively. If a User has posts and a Post has an author, you can nest them infinitely: 

# This query is exponentially expensive
{
  users {
    posts {
      author {
        posts {
          author {
            posts {
              author {
                # ... keeps going — each level multiplies the work
              }
            }
          }
        }
      }
    }
  }
}

Without depth limiting, this query can consume massive amounts of server resources — CPU, memory, and database connections. A single malicious query can take down the entire API. This is a Denial of Service (DoS) attack unique to GraphQL.

Attack #3: Authorization Bypass

In REST, authorization is often enforced at the endpoint level: "only admins can access /api/admin/users." In GraphQL, there is only one endpoint. Authorization must be enforced in every resolver, for every field. 

# DANGEROUS: no auth check — returns ALL posts including private ones
def resolve_posts(root, info):
    return db.execute('SELECT * FROM posts').fetchall()

# SAFE: filter by current user's permissions
def resolve_posts(root, info):
    user = info.context['user']
    if user.is_admin:
        return db.execute('SELECT * FROM posts').fetchall()
    return db.execute('SELECT * FROM posts WHERE author_id=? OR public=1',
                      (user.id,)).fetchall()

Common mistakes: securing a mutation like deleteUser but not the corresponding query that reveals user data, or protecting a resource at one query path (user.privateEmail) but not another (post.author.privateEmail).

Attack #4: SQL Injection via Resolvers

GraphQL does not magically prevent injection. If a resolver builds SQL queries by concatenating user-supplied arguments, it is vulnerable to the same SQL injection as any other application: 

# DANGEROUS: string interpolation in resolver
def resolve_search_users(root, info, name):
    return db.execute(
        f"SELECT * FROM users WHERE name LIKE '%{name}%'"
    ).fetchall()
    # GraphQL query: { searchUsers(name: "' UNION SELECT * FROM secrets--") { ... } }
    # → SQL injection!

Attack #5: Batching and Brute Force

Many GraphQL servers accept arrays of queries in a single HTTP request. This enables:

  • Rate limit bypass: Send 1,000 login attempts in a single HTTP request — if the rate limiter counts HTTP requests, it sees only one
  • Brute force acceleration: Try thousands of passwords, OTP codes, or API keys in batch
// Single HTTP request, 100 login attempts
[
  { "query": "mutation { login(email: \"admin@x.com\", pass: \"pass1\") { token } }" },
  { "query": "mutation { login(email: \"admin@x.com\", pass: \"pass2\") { token } }" },
  { "query": "mutation { login(email: \"admin@x.com\", pass: \"pass3\") { token } }" }
  // ... 97 more
]

Attack #6: Field Suggestion Leaks

Even when introspection is disabled, many GraphQL implementations suggest valid field names when you misspell one. Query for { users { passwor } } and the error might say: "Did you mean 'password' or 'passwordHash'?" This leaks schema information through the back door.

Defense Checklist

  • Disable introspection in production — most frameworks have a one-line config for this
  • Implement query depth limiting — cap at 5-10 levels
  • Query cost analysis — assign costs to fields and reject queries exceeding a budget
  • Per-field authorization in every resolver — never assume a field is "hidden"
  • Parameterized queries in resolvers — same rules as any SQL code
  • Batch size limits — cap array queries at 10-20 operations
  • Rate limiting per operation, not just per HTTP request
  • Disable field suggestions in error messages for production
Impact: GraphQL vulnerabilities can leak entire database schemas, expose private data via authorization gaps, enable DoS through expensive queries, serve as injection vectors through unsafe resolvers, and bypass rate limiting via batching. The single-endpoint architecture means traditional WAF rules and API gateways often miss these attacks entirely.
