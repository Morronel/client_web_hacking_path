Module 19 — Path Traversal

Learn how attackers escape intended directories to read arbitrary files on the server.

Escaping the Sandbox

Path traversal is beautifully simple. The application serves files from a specific directory — say, /app/documents/public/. Users request files by name: /view?file=report.pdf. The server concatenates the filename onto the base path and opens the file. Simple, right?

But what happens when the user requests /view?file=../../../etc/passwd? The server constructs the path /app/documents/public/../../../etc/passwd. The operating system resolves the ../ sequences, climbing up three directory levels, and ends up at /etc/passwd. The attacker just read a file they were never supposed to access.

This is path traversal (also called directory traversal or dot-dot-slash attacks). It exploits the simple fact that ../ means "go up one directory" in every operating system, and many applications do not validate that the resulting path stays within the intended directory.

The Vulnerable Pattern

Vulnerable Code

@app.route('/view')
def view():
    filename = request.args.get('file')
    # DANGEROUS: user controls the filename, can use ../ to escape
    with open(f'documents/public/{filename}') as f:
        return f.read()

# Normal:  /view?file=report.pdf  → opens documents/public/report.pdf
# Attack:  /view?file=../../../etc/passwd → opens /etc/passwd

Safe Code

import os

@app.route('/view')
def view():
    filename = request.args.get('file')
    # Step 1: Strip any path components — only keep the filename
    safe_name = os.path.basename(filename)
    # Step 2: Construct the full path
    full_path = os.path.join('documents/public', safe_name)
    # Step 3: Resolve symlinks and verify the path is still within bounds
    real_path = os.path.realpath(full_path)
    if not real_path.startswith(os.path.realpath('documents/public')):
        abort(403)
    with open(real_path) as f:
        return f.read()

The safe version does three things: (1) os.path.basename() strips all directory components — ../../../etc/passwd becomes just passwd. (2) os.path.realpath() resolves any remaining symlinks or ../ sequences. (3) The startswith() check verifies the resolved path is still within the allowed directory.

Traversal Bypass Techniques

Developers often try to block ../ with simple string replacement. This is almost always bypassable:

PayloadHow It WorksBypasses
../Basic directory-upNo filters
....//After ../ is removed once, becomes ../Single-pass string replace
..././Same trick, different arrangementSingle-pass replace
%2e%2e%2fURL-encoded ../Validation before URL decoding
..%252fDouble URL-encoded (%25 = %)Single decode + check
%00Null byte — truncates string in C-based languagesExtension append (.pdf)
..\/Backslash — Windows treats both / and \ as separatorsFilters checking only /
..%5cURL-encoded backslashWindows + URL decode
The Null Byte Trick: In older versions of PHP, Java, and other C-based runtimes, a null byte (%00) would terminate the string. So if the server appends .pdf to the filename: ../../../etc/passwd%00.pdf → the OS sees ../../../etc/passwd (null byte truncates the rest). Modern runtimes largely fixed this, but it still appears in CTFs and older systems.

High-Value Target Files

When you confirm path traversal, these are the files to go after:

# === Linux ===
/etc/passwd              # User accounts (always readable, confirms traversal)
/etc/shadow              # Password hashes (requires root)
/proc/self/environ       # Environment variables — often contains API keys, secrets
/proc/self/cmdline       # How the process was started
/app/.env                # Application secrets (DB credentials, API keys)
/app/config/database.yml # Rails database config
~/.ssh/id_rsa            # SSH private key
~/.bash_history          # Command history

# === Windows ===
C:\Windows\win.ini       # Always exists, confirms traversal
C:\Windows\system.ini
C:\inetpub\wwwroot\web.config   # IIS configuration with connection strings
C:\Users\Administrator\.ssh\id_rsa
Pro Tip: /proc/self/environ is a goldmine on Linux. It contains all environment variables of the current process, which in modern deployments often include database passwords, API keys, JWT secrets, and cloud credentials. If you can read this file, you likely have enough to fully compromise the application.

Path Traversal Beyond File Reads

Reading files is the most common impact, but path traversal can be more dangerous when combined with other features:

  • File write + traversal: If the application lets you upload/write files and has a traversal bug, you can write a webshell to the web root
  • Log poisoning: Inject PHP code into a log file via a crafted User-Agent header, then use traversal to include the log file via a Local File Inclusion (LFI) vulnerability
  • Source code disclosure: Read the application's source code to find hardcoded credentials, other vulnerabilities, or business logic flaws
Impact: Path traversal exposes source code, configuration files, credentials, API keys, SSH keys, and environment secrets. When chained with file upload or log injection, it can escalate to Remote Code Execution. OWASP rates it as a high-severity vulnerability.
