Module 15 — Server-Side Request Forgery (SSRF)

Learn how attackers abuse server-side HTTP requests to access internal services, cloud metadata, and bypass network firewalls.

What is SSRF?

Server-Side Request Forgery occurs when an application fetches a remote resource using a user-supplied URL without adequate validation. The attacker controls where the server makes requests, turning it into a proxy that can reach internal networks, cloud metadata services, and other resources that are inaccessible from the outside.

Why SSRF is Dangerous

The server typically sits inside a trusted network zone with access to internal services, databases, and cloud infrastructure APIs. An SSRF vulnerability lets an external attacker reach these resources through the server.

Vulnerable Code: Unrestricted URL Fetch

# Flask — VULNERABLE: user controls the URL
import urllib.request

@app.route('/fetch')
def fetch_url():
    url = request.args.get('url')
    response = urllib.request.urlopen(url)  # attacker controls destination
    return response.read()

An attacker can supply internal URLs:

GET /fetch?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/
GET /fetch?url=http://localhost:6379/   (Redis)
GET /fetch?url=file:///etc/passwd

Safe Code: URL Allowlisting

# Flask — SAFE: strict URL validation
from urllib.parse import urlparse

ALLOWED_HOSTS = {'api.example.com', 'cdn.example.com'}

@app.route('/fetch')
def fetch_url():
    url = request.args.get('url')
    parsed = urlparse(url)

    # Enforce HTTPS and allowlisted hosts only
    if parsed.scheme != 'https':
        return 'Only HTTPS allowed', 400
    if parsed.hostname not in ALLOWED_HOSTS:
        return 'Host not allowed', 403

    response = urllib.request.urlopen(url)
    return response.read()

Common SSRF Targets

Cloud Metadata Endpoints

Most cloud providers expose instance metadata at http://169.254.169.254/. This endpoint returns IAM credentials, instance identity, and configuration data:

  • AWS: http://169.254.169.254/latest/meta-data/iam/security-credentials/
  • GCP: http://metadata.google.internal/computeMetadata/v1/ (requires header)
  • Azure: http://169.254.169.254/metadata/instance?api-version=2021-02-01

Internal Services

  • Databases: Redis (:6379), Memcached (:11211), Elasticsearch (:9200)
  • Admin panels: Kubernetes API (:6443), Docker API (:2375)
  • Internal microservices on private IPs

Filter Bypass Techniques

  • IP encoding: 0x7f000001, 2130706433, 0177.0.0.1 all resolve to 127.0.0.1
  • DNS rebinding: A domain resolves to a public IP on first lookup, then to 127.0.0.1 on subsequent lookups
  • URL scheme abuse: file://, gopher://, dict:// protocols
  • Redirects: An external URL that 302-redirects to an internal address bypasses hostname checks
  • IPv6: [::1] is equivalent to 127.0.0.1
  • URL parsing inconsistencies: http://evil.com@127.0.0.1/ may resolve to localhost

Blind SSRF

When the response is not returned to the attacker, the vulnerability still exists. Blind SSRF is confirmed using out-of-band techniques: DNS lookups to attacker-controlled domains, timing differences, or error message variations.

SSRF Impact: Cloud credential theft (full account takeover via stolen IAM keys), internal port scanning, reading sensitive files, accessing internal admin interfaces, pivoting deeper into the network, and remote code execution via vulnerable internal services.
Defense in Depth: Combine URL allowlisting with network-level controls. Use IMDSv2 on AWS (requires session tokens), disable unnecessary URL schemes, and resolve the hostname before making the request to prevent DNS rebinding.
