Module 13 — Cross-Site Request Forgery (CSRF)

Understand how attackers trick authenticated users into performing unintended actions by exploiting the browser's automatic cookie attachment behavior.

How CSRF Works

When a browser makes a request to a site, it automatically attaches all cookies for that domain, including session cookies. CSRF exploits this by tricking an authenticated user into submitting a request to the target application from a malicious page. The server cannot distinguish the forged request from a legitimate one because the session cookie is present.

The Attack Flow

  1. Victim logs into bank.com and receives a session cookie.
  2. Victim visits evil.com while still logged in.
  3. evil.com contains a hidden form that auto-submits a POST to bank.com/transfer.
  4. The browser attaches the session cookie, and the bank processes the transfer.

Same-Origin Policy Gaps

The same-origin policy prevents JavaScript on evil.com from reading responses from bank.com, but it does not prevent cross-origin form submissions or image/script requests. The attacker does not need to read the response; the side effect (transfer, password change) is the goal.

Vulnerable Code: No CSRF Protection

# Flask — VULNERABLE: no CSRF token validation
@app.route('/transfer', methods=['POST'])
@login_required
def transfer():
    to_account = request.form['to']
    amount = request.form['amount']
    db.execute("UPDATE accounts SET balance = balance - ? WHERE user_id = ?",
               (amount, current_user.id))
    db.execute("UPDATE accounts SET balance = balance + ? WHERE user_id = ?",
               (amount, to_account))
    db.commit()
    return redirect('/dashboard')

Safe Code: Flask-WTF CSRF Protection

# Flask — SAFE: CSRF token required
from flask_wtf import FlaskForm, CSRFProtect
from wtforms import StringField, DecimalField

csrf = CSRFProtect(app)

class TransferForm(FlaskForm):
    to = StringField('Recipient')
    amount = DecimalField('Amount')

@app.route('/transfer', methods=['POST'])
@login_required
def transfer():
    form = TransferForm()
    if form.validate_on_submit():  # validates CSRF token automatically
        # process transfer
        pass
    return redirect('/dashboard')
<!-- Template includes hidden CSRF token -->
<form method="POST" action="/transfer">
  {{ form.hidden_tag() }}
  <input name="to" placeholder="Recipient">
  <input name="amount" placeholder="Amount">
  <button type="submit">Transfer</button>
</form>

Defense Mechanisms

CSRF Tokens

A unique, unpredictable token is embedded in each form and validated on the server. Because the attacker cannot read the target page (same-origin policy), they cannot obtain the token.

SameSite Cookies

The SameSite cookie attribute controls whether cookies are sent with cross-site requests:

  • Strict: Cookie is never sent on cross-site requests. Strongest protection but can break legitimate flows.
  • Lax: Cookie is sent on top-level GET navigations but not on POST or embedded requests. Default in modern browsers.
  • None: Cookie is always sent (requires Secure flag). No CSRF protection.

Referer / Origin Header Validation

The server can check the Origin or Referer header to verify the request originates from the same site. However, these headers can be stripped by privacy extensions, proxies, or meta-refresh redirects, so this should not be the sole defense.

JSON CSRF

APIs accepting JSON bodies are sometimes assumed safe from CSRF because forms cannot natively send JSON. However, if the server does not validate the Content-Type header, an attacker can use navigator.sendBeacon() or fetch() with no-cors mode to send form-encoded data that the server parses as JSON.

CSRF Impact: Account takeover (password/email change), unauthorized fund transfers, privilege escalation (adding admin accounts), data modification, and social engineering amplification.
Detection Tip: Look for state-changing endpoints that accept POST/PUT/DELETE without a CSRF token parameter or custom header. Check if SameSite=None is set on session cookies.
