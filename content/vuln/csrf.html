Module 17 — Cross-Site Request Forgery (CSRF)

Understand how attackers trick authenticated users into performing unintended actions by exploiting the browser's automatic cookie attachment behavior.

The Confused Deputy

CSRF is one of the most elegant attacks in web security because it does not exploit a bug in the code — it exploits how browsers fundamentally work. Here is the core issue: when your browser makes a request to bank.com, it automatically attaches all cookies for bank.com, including your session cookie. The browser does this regardless of where the request originated.

So if you are logged into your bank, and you visit a malicious website, that website can make your browser send a request to bank.com/transfer?to=attacker&amount=10000 — and your browser will helpfully attach your session cookie, making it look like a legitimate request from you.

The bank's server sees a valid session cookie and processes the transfer. It has no way to know the request came from evil.com instead of the bank's own page. The browser is the "confused deputy" — it has the authority to act on your behalf (via the session cookie) but is tricked into using that authority for the attacker's benefit.

The Attack Flow, Step by Step

  1. Victim logs into bank.com and receives a session cookie (session=abc123).
  2. Victim visits evil.com (via a link in an email, a forum post, an ad, etc.) while still logged into the bank.
  3. evil.com contains a hidden, auto-submitting form that POSTs to bank.com/transfer.
  4. The victim's browser submits the form. Because the target is bank.com, the browser attaches the session=abc123 cookie.
  5. The bank's server sees a valid session and a valid transfer request. It processes the transfer. The victim never sees anything — the form submission happened automatically and invisibly.
<!-- The attacker's page (evil.com) -->
<html>
<body onload="document.forms[0].submit()">
  <form method="POST" action="https://bank.com/transfer">
    <input type="hidden" name="to" value="attacker-account">
    <input type="hidden" name="amount" value="10000">
  </form>
</body>
</html>
Why Does This Work? The Same-Origin Policy prevents JavaScript on evil.com from reading responses from bank.com. But it does NOT prevent cross-origin form submissions, image loads, or script loads. The attacker does not need to read the response — the side effect (the money transfer) is the goal.

Vulnerable Code

# Flask — VULNERABLE: no CSRF token validation
@app.route('/transfer', methods=['POST'])
@login_required
def transfer():
    to_account = request.form['to']
    amount = request.form['amount']
    # The server trusts the request because the session cookie is valid
    # But it never verifies that the request came from the bank's own page
    db.execute("UPDATE accounts SET balance = balance - ? WHERE user_id = ?",
               (amount, current_user.id))
    db.execute("UPDATE accounts SET balance = balance + ? WHERE user_id = ?",
               (amount, to_account))
    db.commit()
    return redirect('/dashboard')

Defense #1: CSRF Tokens

The most common defense. The server generates a random, unpredictable token and includes it in every form as a hidden field. When the form is submitted, the server verifies that the token is present and correct. Because the attacker cannot read the bank's pages (SOP blocks this), they cannot obtain the token, so their forged form submission will be missing the token and get rejected. 

# Flask — SAFE: CSRF token required
from flask_wtf import FlaskForm, CSRFProtect
from wtforms import StringField, DecimalField

csrf = CSRFProtect(app)

class TransferForm(FlaskForm):
    to = StringField('Recipient')
    amount = DecimalField('Amount')

@app.route('/transfer', methods=['POST'])
@login_required
def transfer():
    form = TransferForm()
    if form.validate_on_submit():  # validates CSRF token automatically
        # process transfer — token is valid, request is genuine
        pass
    return redirect('/dashboard')
<!-- Template includes hidden CSRF token -->
<form method="POST" action="/transfer">
  {{ form.hidden_tag() }}  <!-- renders: <input type="hidden" name="csrf_token" value="random-token-here"> -->
  <input name="to" placeholder="Recipient">
  <input name="amount" placeholder="Amount">
  <button type="submit">Transfer</button>
</form>

Defense #2: SameSite Cookies

The SameSite cookie attribute is a browser-level defense that controls whether cookies are sent with cross-site requests. It is arguably the single biggest improvement to CSRF defense in the last decade.

  • Strict: Cookie is NEVER sent on cross-site requests. Maximum protection, but can break legitimate flows (e.g., clicking a link to the site from an email will not have the session cookie, so the user appears logged out).
  • Lax: Cookie is sent on top-level GET navigations (clicking a link) but NOT on POST forms, iframes, or AJAX requests from other sites. This is the default in modern browsers (Chrome, Firefox, Edge) and provides good CSRF protection for state-changing POST endpoints.
  • None: Cookie is always sent cross-site (requires the Secure flag). No CSRF protection. Only use this for cookies that explicitly need to work cross-site (e.g., OAuth, embedded widgets).
Good News: Since 2020, Chrome, Firefox, and Edge default cookies to SameSite=Lax when no SameSite attribute is specified. This means most new web applications get basic CSRF protection "for free." However, you should still implement CSRF tokens as defense-in-depth, because Lax does not protect against GET-based state changes, and older browsers may not enforce SameSite.

Defense #3: Origin/Referer Validation

The server can check the Origin or Referer HTTP header to verify that the request originated from the same site. This is a useful supplementary defense, but it should not be your only protection because:

  • Privacy extensions may strip the Referer header
  • Some proxies and firewalls modify or remove Origin headers
  • Meta-refresh redirects can bypass Referer checks

JSON APIs and CSRF

A common misconception: "My API only accepts JSON, so it is not vulnerable to CSRF because HTML forms cannot send JSON." This is mostly true in modern browsers with SameSite=Lax, but there are edge cases:

  • If the server accepts Content-Type: text/plain and parses the body as JSON, a form can send enctype="text/plain" with a crafted body
  • navigator.sendBeacon() can send arbitrary content types in some configurations
  • If SameSite=None is set on the session cookie, fetch() with credentials: 'include' can send JSON cross-origin (though the server must also set permissive CORS headers)
Best Practice: For JSON APIs, require a custom header like X-Requested-With: XMLHttpRequest. Custom headers cannot be set by HTML forms, so their presence proves the request came from JavaScript on your own site (or a site allowed by your CORS policy). This is sometimes called the "double-submit" pattern for APIs.
CSRF Impact: Account takeover (changing the victim's email or password), unauthorized fund transfers, privilege escalation (making the victim add the attacker as an admin), data modification (deleting resources, changing settings), and social engineering amplification (making the victim post content they did not write).
