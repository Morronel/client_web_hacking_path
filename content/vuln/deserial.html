Module 16 — Insecure Deserialization

Understand how untrusted serialized data can lead to remote code execution through Python pickle, YAML, and custom object injection.

The Most Underrated Vulnerability

Deserialization vulnerabilities are weird because they do not look like other vulnerabilities. There is no injection point in a form field. There is no URL parameter to tamper with. Instead, the attack vector is a blob of binary or encoded data — a cookie, an API parameter, a file upload — that the application deserializes (converts from bytes back into an object) using an unsafe method.

The consequence? Remote Code Execution. Not "maybe" or "under certain conditions." Just straight RCE. The attacker crafts a serialized object that, when deserialized, executes arbitrary commands on the server. No authentication needed, no SQL query involved, no browser interaction — just send the payload and get a shell.

This is why insecure deserialization has been in the OWASP Top 10 since 2017. It is not the most common vulnerability, but when you find it, the impact is almost always critical.

Serialization 101

Let us start with the basics. Serialization converts an in-memory object into a format that can be stored or transmitted (bytes, strings, JSON). Deserialization reverses this — it takes the stored format and reconstructs the original object.

Every programming language has serialization mechanisms. Some are safe (JSON — only handles basic data types). Some are incredibly dangerous (Python's pickle, Java's ObjectInputStream, PHP's unserialize) because they can reconstruct arbitrary objects, including objects that execute code as part of their construction.

Analogy: Imagine receiving a package in the mail. JSON serialization is like receiving a box of LEGO bricks — harmless data that you assemble yourself. Pickle serialization is like receiving a fully assembled device that plugs itself in and starts running the moment you open the box. If someone mailed you a bomb, you would not want a package format that auto-detonates on opening.

Python Pickle — The Classic Example

Python's pickle module is the textbook example of dangerous deserialization. It can serialize and deserialize any Python object, and it uses a special method called __reduce__ to control how objects are reconstructed. The key insight: __reduce__ can return any callable, and that callable is invoked during deserialization.

Vulnerable Code

import pickle, base64

@app.route('/load', methods=['POST'])
def load_data():
    data = request.form.get('data')
    # DANGEROUS: deserializes untrusted data
    # pickle.loads() will execute ANY code embedded in the payload
    obj = pickle.loads(base64.b64decode(data))
    return str(obj)

The Exploit

import pickle, base64, os

class Exploit:
    def __reduce__(self):
        # This method is called during deserialization
        # It returns a tuple: (callable, args)
        # pickle will call: os.popen('cat /etc/passwd')
        return (os.popen, ('cat /etc/passwd',))

payload = base64.b64encode(pickle.dumps(Exploit())).decode()
print(payload)  # Send this to the vulnerable endpoint

# When the server runs pickle.loads() on this payload,
# it calls os.popen('cat /etc/passwd') — RCE achieved.

That is it. Five lines of exploit code. The attacker creates an object whose __reduce__ method returns (os.popen, ('cat /etc/passwd',)). When pickle.loads() deserializes this object, it calls os.popen('cat /etc/passwd'). The server faithfully executes the command and returns the output. Game over.

Safe Alternative

import json

@app.route('/load', methods=['POST'])
def load_data():
    data = request.form.get('data')
    # SAFE: JSON only handles basic types (strings, numbers, lists, dicts)
    # It CANNOT execute code during parsing — there is no __reduce__ equivalent
    obj = json.loads(data)
    return str(obj)
The Python docs literally warn you: The official Python documentation says: "Warning: The pickle module is not secure. Only unpickle data you trust." Despite this warning, developers regularly use pickle to deserialize user-supplied data — in cookies, API parameters, message queues, and cache stores.

YAML Deserialization

Python's YAML library has the same problem. The yaml.unsafe_load() function (and yaml.load() with certain loaders) can instantiate arbitrary Python objects from YAML syntax: 

# DANGEROUS: yaml.unsafe_load() can execute code
import yaml
data = yaml.unsafe_load(user_input)
# Attack payload: !!python/object/apply:os.popen ['cat /etc/passwd']
# The !! syntax tells YAML to construct a Python object

# SAFE: yaml.safe_load() only allows basic types (strings, numbers, lists, dicts)
data = yaml.safe_load(user_input)

Java Deserialization — The Enterprise Nightmare

Java's ObjectInputStream has the same fundamental problem as Python's pickle, but the impact has been far larger because Java is used extensively in enterprise software. In 2015, researchers from Foxglove Security published a paper showing that nearly every major Java framework (Apache Commons Collections, Spring, WebSphere, JBoss, WebLogic) contained "gadget chains" — sequences of objects that, when deserialized, would chain together to execute arbitrary commands.

The tool ysoserial automates the generation of these payloads. You specify the target library and the command you want to run, and it generates a serialized Java object that achieves RCE when deserialized.

Real Story — Equifax Breach (2017): The Equifax breach that exposed 147 million Americans' personal data (including Social Security numbers) was caused by a deserialization vulnerability in Apache Struts (CVE-2017-5638). An attacker sent a crafted Content-Type header containing an OGNL expression that was deserialized and executed on the server. Equifax had not patched a known vulnerability for over two months.

Cookie-Based Deserialization

A common pattern: the application stores user state in a signed cookie. The cookie contains serialized data (often base64-encoded pickle or PHP serialized objects). The server signs the cookie with an HMAC to prevent tampering. Sounds safe, right?

The problem: if the signing key is weak or leaked, the attacker can forge the cookie. Flask uses a session cookie signed with the application's SECRET_KEY. If that key is something like "secret" or "development" or left as the framework default, tools like flask-unsign can crack it and forge cookies with arbitrary data — including pickle payloads. 

# Crack a Flask session cookie's signing key
flask-unsign --unsign --cookie "eyJ..." --wordlist rockyou.txt

# Forge a new cookie with a malicious payload
flask-unsign --sign --cookie '{"admin": true}' --secret 'cracked-key'
Defense: The rules are simple: (1) Never deserialize untrusted data with pickle, yaml.unsafe_load, Java ObjectInputStream, PHP unserialize, or any format that can instantiate arbitrary objects. (2) Use JSON for data interchange — it only handles primitive types and cannot execute code. (3) If you must use signed cookies, use a strong, random SECRET_KEY (at least 32 bytes of entropy). (4) Keep your frameworks patched — deserialization gadget chains are discovered regularly.
