Module 09 — Broken Authentication

Discover how poor authentication implementations leak information and enable credential attacks.

Why Authentication Is the #1 Target

Here is a stat that should keep you up at night: according to the Verizon Data Breach Investigations Report, over 80% of data breaches involve stolen or compromised credentials. Not some clever zero-day exploit. Not a sophisticated supply chain attack. Just... bad passwords, leaked credentials, and login forms that give away too much information.

Think about it. Every single web application has a login page. Every. Single. One. It is the front door, and it is the first thing attackers look at. If your authentication is broken, nothing else matters. You can have the best firewall, the most secure code, the fanciest WAF in the world — if someone can just log in as admin with admin/password123, all of that is worthless.

Authentication answers the question: "Who are you?" It is the process of verifying that a user is who they claim to be. And it turns out that verifying identity over an untrusted network is genuinely hard. There are so many ways to get it wrong.

Fun Fact: The concept of "something you know, something you have, something you are" (the three factors of authentication) was formalized in a 1984 paper, but humans have been using these factors for thousands of years. Ancient Roman soldiers used watchwords (something you know), seals on documents (something you have), and face recognition at the gate (something you are).

Authentication vs. Authorization

Before we go further, let me clear up one of the most commonly confused concepts in security. These two words sound similar but mean very different things:

  • Authentication (AuthN): "Who are you?" — Proving your identity (logging in)
  • Authorization (AuthZ): "What can you do?" — Checking your permissions (accessing resources)

A bouncer at a club checks your ID — that is authentication. Then they check if you are on the VIP list — that is authorization. You can be perfectly authenticated (the bouncer knows who you are) but not authorized (you are not on the list). And vice versa: just because you are authorized to be in the VIP section does not mean anyone verified your actual identity.

This module covers authentication failures. The next module (IDOR) covers authorization failures. They are closely related, but they break in different ways and require different fixes.

Username Enumeration — The Information Leak That Starts Everything

Imagine you are an attacker. You want to break into someone's account on a website. You have no idea what usernames exist. So you go to the login page and type admin as the username with a random password. The server responds: 

"Invalid password for this account"

Wait. Did you catch that? The server just told you that the username "admin" exists. It did not say "invalid username or password" — it specifically said the password was wrong, which means the username was right. Now you try nonexistent_user: 

"User not found in the system"

And there it is. Two different error messages. One tells you the username exists, the other tells you it does not. You have just discovered username enumeration — one of the most common authentication vulnerabilities, and one that most developers create without even thinking about it.

"But wait," you might think, "what is the big deal? So they know a username exists. They still do not have the password." True. But knowing which usernames are valid is the first step to a targeted attack. Instead of guessing both username AND password (impossible at scale), the attacker now only needs to guess the password for a known user. That is a much, much smaller problem.

How Username Enumeration Leaks

Error messages are the most obvious vector, but they are not the only one. Here are all the ways applications accidentally reveal whether an account exists:

Error message"Incorrect password""User not found"
Response time~500ms (bcrypt password check)~10ms (quick reject, no hash computed)

HTTP status code401 Unauthorized404 Not Found
Registration page"Username already taken"Registration succeeds
Password reset"Reset link sent to your email""No account found"
Response body size4,231 bytes4,198 bytes (slightly different HTML)

The timing attack is particularly sneaky. Even if the error messages are identical, if the server takes 500ms when the username is valid (because it is computing a bcrypt hash to check the password) but only 10ms when the username is invalid (because it stops early), an attacker can measure the response times and figure out which usernames exist. This is called a timing side-channel.

Think About It: Your registration page says "This email is already in use." Seems harmless, right? But an attacker can now check whether any email address is registered on your platform. For a dating site or a medical portal, that is a significant privacy violation.
The Fix: Always return a generic message: "Invalid username or password" regardless of which field was wrong. For registration, say "If this email is not already registered, you will receive a confirmation". For password reset, say "If an account exists with that email, a reset link has been sent". Use constant-time comparison so that checking a valid vs invalid username takes the same amount of time.

Password Attacks — The Brute Reality

Once an attacker knows which usernames are valid, the next step is cracking the password. There are several approaches, and understanding the differences is important because each requires a different defense.

Brute Force

The simplest approach: try every possible password for a target account. Start with a, then b, then c... then aa, ab, ac... and keep going. With a fast enough computer, you will eventually find the right password.

The problem? Math. A password with 8 lowercase characters has 26^8 = 208 billion possible combinations. At 1,000 guesses per second against a remote server (a realistic online rate), that would take 6,600 years. So pure brute force against online systems is not practical — but against offline password hashes, modern GPUs can try billions of hashes per second, making it very real.

Dictionary Attacks

Humans are terrible at choosing passwords. Instead of trying every possible combination, just try the passwords humans actually use. The infamous rockyou.txt wordlist contains 14 million real passwords leaked from the RockYou breach in 2009. Using that list, you can crack a significant percentage of accounts in minutes.

Real Story: In 2009, the social app RockYou stored 32 million user passwords in plaintext — no hashing, no encryption, nothing. When the database was breached, the entire password list was leaked. Security researchers analyzed it and found that the most common password was 123456 (used by 290,731 accounts). The rockyou.txt file became the go-to wordlist for password cracking and is still used in every penetration test today, over 15 years later.

Credential Stuffing

Here is where it gets really scary. Remember how people reuse passwords? If someone uses hunter2 on LinkedIn AND their email AND their banking app, and LinkedIn gets breached... the attacker now has a valid username/password combo that works on ALL their accounts. This is credential stuffing: taking leaked credentials from one breach and trying them on other sites.

The "Collection #1" leak in 2019 contained 773 million unique email addresses and 21 million unique passwords. That is a massive credential stuffing database, and attackers actively trade and use these lists.

Password Spraying

Most account lockout mechanisms trigger after N failed attempts for one account — say, 5 failed logins and the account is locked for 30 minutes. Password spraying works around this by trying ONE common password against MANY accounts. Try Summer2024! against every account. If nobody gets locked out, try Password1 against every account. You only need one to succeed.

This is devastatingly effective against corporate environments where users are forced to include uppercase, lowercase, numbers, and special characters. What does every user do? CompanyName2024! or Season+Year!. Password spraying exploits this human predictability.

Password Storage — How It Goes Wrong

Even if your users choose strong passwords, it all falls apart if you store them incorrectly. Here is the evolution of password storage, from worst to best:

Level 0: Plaintext (Please Never Do This)

-- The worst possible approach
INSERT INTO users (username, password) VALUES ('admin', 'sunshine');

If the database is breached, every password is immediately exposed. No cracking needed.

Level 1: Simple Hashing (Still Bad)

# Better but still breakable
import hashlib
hashed = hashlib.sha256(password.encode()).hexdigest()
# Problem: same password always produces same hash (rainbow tables)

Level 2: Salted Hashing (Getting Warmer)

# Much better — unique salt per user defeats rainbow tables
import hashlib, os
salt = os.urandom(16)
hashed = hashlib.sha256(salt + password.encode()).hexdigest()
# Problem: SHA-256 is too fast — GPUs can compute billions per second

Level 3: bcrypt/argon2 (The Right Way)

# Best practice — intentionally slow hashing
import bcrypt
hashed = bcrypt.hashpw(password.encode(), bcrypt.gensalt(rounds=12))
# Each hash takes ~250ms — makes brute force impractical
# bcrypt includes the salt in the output automatically
Real Story: In 2013, Adobe was breached and 153 million user records were leaked. They did not use plaintext, but they used 3DES encryption in ECB mode instead of proper hashing. ECB mode encrypts identical inputs to identical outputs, so researchers could see that millions of users had the same password (it was 123456) without even cracking the encryption. The password hints (stored in plaintext!) helped crack the rest. It was one of the most instructive examples of how NOT to store passwords.

Defenses — Building Authentication Right

After all that doom and gloom, here is how to build authentication that actually works:

For Login Forms

  • Uniform error messages: "Invalid username or password" — same text, same HTTP status, same response size, same response time
  • Rate limiting: After N failed attempts, add exponential delays (1s, 2s, 4s, 8s...)
  • Account lockout: Lock after 10-20 failed attempts, require email verification to unlock
  • CAPTCHA: After 3-5 failed attempts, show a CAPTCHA challenge
  • Constant-time comparison: Use hmac.compare_digest() in Python or crypto.timingSafeEqual() in Node.js to prevent timing attacks

For Password Storage

  • Use bcrypt, scrypt, or argon2 — never MD5, SHA-1, or even SHA-256 for passwords
  • Set a high work factor — bcrypt rounds=12+ means each hash takes ~250ms, making brute force impractical
  • Salt automatically — bcrypt and argon2 handle salting internally

Multi-Factor Authentication (MFA)

Even the best password can be phished, leaked, or guessed. MFA adds a second factor:

  • TOTP apps (Google Authenticator, Authy): Time-based one-time passwords. Good security, reasonable usability.
  • Hardware keys (YubiKey, FIDO2/WebAuthn): Physical device must be present. Best security, phishing-resistant.
  • SMS codes: Better than nothing, but vulnerable to SIM-swapping attacks where an attacker calls your phone carrier, pretends to be you, and transfers your number to their SIM card.
The Bottom Line: Authentication is the #1 attack surface on any web application. Most breaches start with a compromised credential. Build your login system as if every attacker in the world is going to try to break it — because they will.
